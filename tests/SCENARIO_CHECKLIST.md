# 场景清单测试法（Scenario Checklist）

> 改任何「计费 / 权限 / 显示」逻辑前，先照本清单核对，再写断言。
> 核心原则：不要问「代码跑通了吗」，要问「用户会遭遇什么情况」。
> 每踩一次新坑，就把坑补进清单——清单是从事故里长出来的规则，不是手写拍脑袋。

## 一、计费 / 改价类（带「时间」维度）

凡是涉及涨价、优惠、过期、新旧价、余额扣减，必须覆盖以下时点的用户：

- [ ] **存量**：改价前已买/已充的 → 按旧价（守承诺）
- [ ] **新充**：改价后新买/新充的 → 按新价
- [ ] **混合**：旧账没花完又充了新账 → 分段计价（旧积分按旧价抵扣，剩余按新价）
- [ ] **非购买发放**：补偿/退款/赠送 → 明确「算旧价还是新价」，且和发放口径一致
- [ ] **边界**：余额刚好不够一整单 → 分段/报余额不足，不能「少积分干多活」占便宜
- [ ] **时点临界**：正好在改价生效日当天/临界值 → 明确定义（含「当天算哪边」）

## 二、权限 / 身份类（带「身份」维度）

凡是「老用户 / 新用户 / 未登录 / 管理员」的逻辑，必须测每种身份 × 每种状态，且**未登录要连源码一起查**（不能只看页面上有没有显示框）：

- [ ] **未登录** → 看不到；且**源码里也没有相关字样**（不只是 DOM 不渲染）
- [ ] **新用户** → 看不到 / 看到正确提示（不能让他误以为自己有资格）
- [ ] **老用户未处理** → 看到可操作入口
- [ ] **老用户已处理** → 看到「已处理」态
- [ ] **反复操作** → 幂等，不重复发放/不重复扣费

## 三、显示 / 文案类（带「误解」维度）

凡是公告、通知、提示、价格说明，都要做一轮「误解测试」：

- [ ] **不知情的新用户看到会不会误会** → 会不会以为自己也送/也有
- [ ] **三问讲全**：为什么给 / 给谁 / 给多少（缺一个都会让人猜）
- [ ] **注释与实现一致** → 别「注释说一套、代码做一套」

## 怎么用

1. 改代码前，先圈出本次改动属于哪一类（可能跨多类）。
2. 逐条把「用户会遇到的 N 种情况」列出来，为每种情况写一个断言。
3. 测试用例围绕「用户场景」设计，而不是围绕「代码分支」设计。
4. 交付时，对照本清单自检一遍再上线。
