# 200 行的小项目要不要做代码审查：安全风险不看行数，看 6 个接口入口

先给结论：做不做代码审查，跟项目写了多少行没有关系。它跟三件事有关——外面能摸到几个入口、入口后面放着什么数据、这套东西能不能被不特定的人连上。行数记录的是「我们写了多少」，暴露面记录的是「别人能碰多少」。这两件事从来不成正比。

「才 200 行，不用审」这句话在小团队里特别常见。它听起来像是省时间，实际上是把判断依据换错了：把「工作量小」当成了「后果小」。一个内部备忘录小服务，只要按编号能读别人的记录、把环境变量回给调用方、把凭据打进日志，后果跟它是 200 行还是二十万行没有一点关系。

我写了一个故意留问题的示例服务用来验证这件事：两个文件，`app.py` 92 行、`requirements.txt` 3 行，纯标准库，没有框架、没有数据库、没有前端。再用一个 100 行出头的静态清点脚本跑一遍，不启动服务、不联网、不装包，只解析抽象语法树和文本。实跑输出如下（数字全部来自这次运行，不是估算）：

```text
项目文件：2 个（app.py + requirements.txt）
物理行数：95（app.py 92 行 + requirements.txt 3 行）
有效代码行：69（app.py）
外部入口（ROUTES）：6  ->  /health /note /note/delete /admin/export /debug/env /login
碰到数据/环境变量的入口：5  ->  /note /note/delete /admin/export /debug/env /login
其中带身份或归属判断：0  ->  （无）
硬编码凭据字面量：3  ->  dev-secret-2026 tok_alice_001 tok_bob_002
危险配置命中：4  ->  DEBUG=True、CORS="*"、凭据进日志、堆栈回传
依赖声明：3 条，未固定版本：2  ->  requests>=2.31 flask
```

95 行，6 个外部入口，5 个碰到数据，0 个归属判断。这就是「小」的真实含义。

## 一、行数不是判据，官方标准也不是按行数分级的

OWASP 应用安全验证标准（ASVS）5.0.0 于 2025-05-30 发布，官方 CSV 里是 17 章、345 条可逐条验证的要求，分成三级。按 OWASP DevSecOps Guideline 的表述，Level 1 是「适合所有应用」的最低基线，覆盖基础安全卫生；Level 2 面向处理敏感数据的多数业务应用；Level 3 面向金融、医疗、关键基础设施这类高保证系统。选级看的是数据敏感度、业务影响和威胁模型，**标准里没有任何一条按代码行数划档**。ASVS 官方项目页还写明，它既用来测试 Web 应用的技术安全控制，也给开发者一份安全开发要求清单，还能作为采购验收的依据——三种用途都不问项目多大。

OWASP Top 10:2025 同样把根因指向结构，不是规模：

- **A01 失效的访问控制**仍居第一，官方 A01 页面把它描述为「没有限制或错误地限制了对资源的访问」，典型形态包括改 URL 参数、改内部状态、按唯一标识读别人的记录、缺鉴权的写接口、CORS 配置过宽。
- **A02 安全配置错误**从 2021 版的第 5 位升到 2025 版的第 2 位。官方页面列的触发形态是：默认账号和密码没改、不必要的端口/服务/页面/测试框架还开着、错误响应把堆栈回给用户、缺少安全响应头、升级后新安全特性没启用。
- **A03 软件供应链失效**由「易受攻击和过时的组件」扩展而来，覆盖第三方依赖、构建系统与分发基础设施。
- **A09 安全日志记录和告警失效**、**A10 异常条件处理不当**也在榜单里。

这五类里，没有一类的成立条件是「代码够多」。一个只有健康检查接口的服务，可能因为调试端点没关而踩中 A02；一个只有三行依赖声明的项目，照样落在 A03 的范围内。用行数决定审不审，等于用体重决定要不要体检。

## 二、把那 95 行拆开：6 个入口，5 个碰数据，0 个判断

示例服务的路由表很短，短到可以整张摆出来：

| 入口 | 碰到什么 | 缺的那一步 |
|---|---|---|
| `/health` | 无数据 | 无（公开探活，本就不用鉴权） |
| `/note` | 按编号取备忘录字典 | 取出后没比较 `owner` 与当前身份，改个编号就能读别人的记录 |
| `/note/delete` | 删同一份字典 | 连身份都没读，谁都能删 |
| `/admin/export` | 全部备忘录 + 全部凭据 | 没有角色判断，还把凭据列表放进响应 |
| `/debug/env` | 进程环境变量 | 调试端点留在路由表里，环境变量整包回传 |
| `/login` | 凭据字典 | 把 token 打进日志，日志通常比代码活得更久、传得更广 |

外加异常分支里一句 `traceback.format_exc()` 直接写回响应体，模块顶上还有 `DEBUG = True` 和 `ALLOW_ORIGIN = "*"`。

值得停一下的是：**这 6 个入口出的问题不是同一类**。按编号读别人的记录属于访问控制；调试端点、默认开关、堆栈回传属于配置；硬编码凭据和日志打印属于凭据管理；异常响应属于错误处理；`requests>=2.31` 和没写版本的 `flask` 属于依赖与供应链。人肉「通读一遍 95 行」时，注意力很容易全被第一类吸走，因为它是唯一长得像「业务逻辑」的那一处。剩下四类散落在文件头、异常分支、日志语句和一个 3 行的文本文件里，不在同一屏、不在同一种语法结构里，靠读代码顺序扫过去会一条条漏掉。

所以审查清单的组织方式得改：按**风险类别**铺开，不按**文件顺序**走，也不按行数收窄范围。

## 三、四类不看行数的风险源，各自该怎么核

**配置与默认值（A02）。** 官方给的防护动作很具体：可重复的加固流程、开发/测试/生产三套环境配置一致但凭据不同、最小化平台（不用的功能、组件、示例应用、文档都别装）、统一拦截过度详细的错误信息、自动验证配置有效性。对小项目最实用的三问：调试开关关了没、示例应用和示例账号删了没、错误响应里还有没有堆栈。这三问跟代码量无关，跟部署时复制了哪份配置有关。

**凭据与日志（A02、A09）。** A02 官方明确建议用平台提供的身份联邦、短期凭据或基于角色的访问机制，替代把静态密钥写进代码、配置文件或流水线。落到检查上就是两层：代码里有没有以 `dev-secret`、`tok_` 这类形态出现的字面量；日志语句里有没有把 token、请求体、环境变量整包打出去。凭据一旦进日志，就会进日志采集、进备份、进别人的检索框，这时候改代码已经来不及了。

**依赖与构建（A03）。** 小项目的依赖树常常比自己的代码大得多。Python 侧的 `pip-audit` 由 PyPA 维护，官方 README 写它能审计当前环境、requirements 文件、本地项目，默认经 PyPI JSON API 查 Python 打包咨询库，也能切到 OSV，输出 CycloneDX 格式的 SBOM，还能 `--fix`。npm 侧官方 `npm audit` 会把项目依赖描述提交给默认 registry 拿已知漏洞报告，默认需要 `package-lock.json` 或 shrinkwrap；官方特别提醒，绕过锁文件后每次运行重建依赖树，结果会不一样。两个工具都要在 CI 里跑，理由不是「这次有漏洞」，而是新的公告会在你代码一行没改的前提下让构建变红。

这里有个边界得说清楚：这类工具比对的是**已知公告与版本**，它不看你代码里有没有真的调用那个危险函数，也挡不住还没进公告库的恶意包。`pip-audit` 官方安全模型还提醒，用 `-r` 会解析依赖，等价于 `pip install`，别拿不信任的 requirements 文件去跑。把「扫描通过」读成「代码安全」，是把工具的能力范围擅自放大了一圈。

**异常与错误响应（A10、A02）。** 示例里那个 `except` 分支是典型写法：为了排查方便把堆栈回给调用方，顺手把内部路径、组件版本、环境信息一起送出去。正确形态是统一返回泛化错误，细节只落服务端日志，并且异常路径默认拒绝而不是默认放行。

## 四、一份 30 分钟能跑完的自检清单

下面每一条都能对着文件或命令打勾，不依赖评审者当天状态好不好。顺序按「先划范围，再查形态」排：

1. **先把入口清单拉全。** 从路由表、装饰器、网关配置三处分别取一遍，合并去重。旁路最容易漏：文件、导出、预览、独立部署的调试服务。
2. **每个入口写一行「谁能调 / 读谁的什么数据 / 拒绝时返回什么」。** 写不出第二格的，标为待补证据，不许留空。
3. **身份来源只认服务端。** 请求体里的 `user_id`、`tenant_id`、前端传的角色字段，不能当归属条件用。
4. **按编号读取时，归属条件和编号进同一个查询。** 先查出来再在内存里判，遇到批量接口和缓存层很容易被绕开。
5. **负向用例至少四条**：未登录、换账号、换租户、编号 ±1 重放，期望 403 或 404。响应别让「不存在」和「无权访问」给出不同状态码。
6. **凭据与危险配置扫一遍**，命令给出的是形态，不是结论：

```bash
git grep -nE '(SECRET|TOKEN|PASSWORD|API_KEY)[[:space:]]*=' -- '*.py' '*.js' '*.yaml' '*.yml'
git grep -nE 'DEBUG[[:space:]]*=[[:space:]]*True|ALLOW_ORIGIN[[:space:]]*=[[:space:]]*"\*"|format_exc\('
git grep -n 'print(' -- '*.py' | grep -iE 'token|secret|password|header|body'
```

7. **依赖锁版本并跑公告库核对**：`pip-audit -r requirements.txt`、`npm audit --json`；把命令写进 CI，锁文件进版本库。结果只说明「已知公告里没匹配到」，别当成更宽的承诺。
8. **确认公网可达性**：监听地址是不是只绑内网、管理后台和示例应用有没有暴露、云存储权限是不是默认开放。这一条决定了前面所有问题的后果量级。

这八条里，第 1、3、4、5 条是访问控制，第 6 条横跨凭据、配置、日志，第 7 条是供应链，第 8 条是暴露面。一份清单覆盖的类别，比「把代码从头读到尾」更全。先初筛，再上线。

## 五、什么时候从自检升级成正式审查

自检是所有项目都要做的基线，跟大小无关；升级与否看三个触发条件，满足任意一条就该按更高等级逐条验证：

- **数据**：出现第三方个人信息、身份信息、支付或合同数据 → 对应 ASVS Level 2 的场景。
- **后果**：接口能改动资金、权限、他人数据或对外披露内容 → 影响面已经超出项目本身。
- **可达**：公网可达、跨租户、被其它系统调用 → 调用方不受你控制，输入不可预期。

还有一条二阶影响容易被忽略：小项目不会一直小。它会被复制成新服务的骨架、被接进内网、被挂到公网、被塞进交付包给甲方。今天用「才 200 行」省下的那半小时，会变成后面每加一个入口都要回头补的债，而且补的时候已经没人记得当初为什么留了 `DEBUG = True`。把清单写进提交前的自动检查，是一次性成本；靠每次有人想起来通读一遍，是长期成本。

## 六、实验怎么复现

清点脚本只做一件事：把上面那些形态变成可复核的计数。它用 `ast` 从模块级字典字面量自动认出「数据源」，不是手写一张路由白名单；路由表也从 AST 里读，所以加一个入口、删一个判断，数字会跟着变。

```python
def names_in(node):
    out = set()
    for sub in ast.walk(node):
        if isinstance(sub, ast.Name):
            out.add(sub.id)
        elif isinstance(sub, ast.Attribute):
            out.add(sub.attr)
    return out


def has_identity_decision(node):
    for sub in ast.walk(node):
        if isinstance(sub, (ast.If, ast.Compare, ast.BoolOp)):
            if any(w in w2 for w in IDENTITY_WORDS for w2 in names_in(sub)):
                return True
    return False
```

把 `app.py`、`requirements.txt`、`audit.py` 放同一个目录，跑 `python audit.py .`，就能得到开头那组输出。实验过程没有启动那个 HTTP 服务，也没有发过任何网络请求；示例服务绑定的是 `127.0.0.1`，属于刻意留问题的反面材料，别拿去部署。

这个脚本只负责数数，不负责替谁定性。「6 个入口」是事实，「风险可不可接受」是团队按数据和场景做的决定。把这两件事分开，清单才不会变成走过场的表单——计数可以每次自动跑，定性必须有人签字。

## 把清单固定下来

95 行代码里能同时躺着 6 个外部入口、3 条硬编码凭据和 4 处危险配置，靠「项目小，不用审」这句话，一条都挡不住。

能机械判的那几项，交给每次都跑的检查更靠谱。路由清单有没有逐条写清谁能调、身份是不是从服务端会话取、按编号读取有没有把归属条件写进同一个查询、默认账号与调试开关关没关、堆栈和凭据有没有进响应或日志、依赖有没有锁版本并跑过公告库核对。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事：7 大规则引擎把能从代码结构里读出来的形态逐条跑一遍。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
