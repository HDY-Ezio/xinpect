# 外包项目代码交付验收清单：甲方该验的不是功能演示，是接口里越权漏洞的证据

验收会开得很顺。外包方把功能从头演示到尾，每个按钮都有反应，测试用例全绿，文档齐整，源码打包交了，尾款签字付掉。三个月后运营发现，换个订单编号就能查到别家公司的订单明细。回头翻验收记录，那天的每一项都写着「通过」。

问题不在验收不认真，在验收清单里根本没有「换一个身份会怎样」这一项。演示证明的是系统**能做什么**，出事的地方是系统**没拦什么**。少写的那行判断不会出现在任何一条功能用例里，也不会出现在演示画面上。

甲方通常不写代码，这反而更要把要求写成能收的文件和能跑的测试，而不是「代码质量良好」这种没法核对的结论。下面按「为什么漏 → 收什么 → 怎么核 → 条款怎么写 → 最小动作」拆开。

## 一、演示全过，为什么风险还在

验收环境和真实运行之间至少有三处系统性差异，每一处都会把越权问题藏起来。

**身份差异。** 演示常用一个高权限账号走全程，生产里是多个租户、多种角色的普通用户。OWASP API Security Top 10 2023 的 API5:2023（Broken Function Level Authorization）说的正是这类：管理功能与普通功能混在一起、层级和角色划分不清，攻击者就能调到本不该调的功能。演示用管理员账号，这条路径永远不会被走到。

**数据差异。** 演示库里往往只有一个租户的数据。「只能看自己的」和「能看自己的」，在只有一个账号的库里表现完全一样。

**路径差异。** 演示走正常路径，攻击者走的是没画的那条。看一段 FastAPI 的查询接口：

```python
@app.get("/api/orders/{order_id}")
def get_order(order_id: int, db: Session = Depends(get_db)):
    return db.query(Order).filter(Order.id == order_id).first()
```

语法、参数化查询、异常处理都没问题。缺的是一句业务判断：这个订单是不是当前登录人的、属于哪个租户。补完之后归属条件和 ID 得落进同一个查询：

```python
@app.get("/api/orders/{order_id}")
def get_order(order_id: int,
              user: User = Depends(current_user),
              db: Session = Depends(get_db)):
    return (db.query(Order)
              .filter(Order.id == order_id,
                      Order.tenant_id == user.tenant_id,
                      Order.owner_id == user.id)
              .first())
```

OWASP 对 API1:2023（Broken Object Level Authorization）的表述很具体：凡是**用用户传来的 ID 去访问数据源**的函数，都应该做对象级授权检查。上面第一行代码恰好符合这个描述，而功能测试用例通常只断言「传自己的 order_id 能查到」，不断言「传别人的 order_id 查不到」。这两条是不同断言，验收单上往往只有第一条。

还有一层更容易漏：API3:2023（Broken Object Property Level Authorization）管的是字段级。接口返回整个对象，把不该给的字段（成本价、证件号、内部备注）一起带出去，功能测试照样全绿，因为它只验「有返回」。

所以验收要问的不是「功能通不通」，是「换身份、换租户、换字段之后，哪一条会被挡住，挡住的记录在哪」。

## 二、把「验什么」写成能收的文件

国内甲方手里其实有一份现成骨架：GB/T 22239-2019（等保 2.0）「安全建设管理」下的四个控制点，原文就是对着外包场景写的。把它逐条翻译成甲方应收到的东西：

| 控制点 | 标准要求（原意） | 甲方应收到的产物 | 缺了会怎样 |
|---|---|---|---|
| 外包软件开发 | 交付前检测可能存在的恶意代码；提供软件设计文档和使用指南；提供源代码并审查后门和隐蔽信道 | 源码包、恶意代码检测记录、设计文档与使用指南、后门与隐蔽信道审查说明 | 只拿到能跑的程序，出事无法定位 |
| 测试验收 | 制订测试验收方案并依方案实施，形成测试验收报告；上线前做安全性测试并出具安全测试报告 | 验收方案、验收报告、上线前安全测试报告（含具体用例与结论） | 报告只剩一句「通过」，无法复核 |
| 系统交付 | 制定交付清单并清点设备、软件和文档；对运维人员培训；提供建设过程文档和运行维护文档 | 交付清单（逐项可勾）、培训记录、建设过程与运维文档 | 交接靠口头，人员一换就断 |
| 服务供应商选择 | 签订协议，明确整个服务供应链各方需履行的网络安全相关义务 | 合同附件里写明第三方组件的清单义务与升级责任 | 组件是外包方引的，出事没人认 |

这四条解决的是「东西齐不齐」，还不解决「权限对不对」。要再补三样，都是能交文件、能翻页核对的：

**授权矩阵。** 角色 × 资源 × 操作，一格一个结论，写上结论落在哪个文件的哪一段；表里没写的操作按拒绝处理。OWASP ASVS 5.0 的 V8 授权章节把控制目标写成：授权规则要形成文档，包含决策因素和环境上下文，使用者只能访问其权限允许的资源。Authorization Cheat Sheet 进一步要求：应用收到访问请求时不能保持中立，必须做出允许或拒绝的决定，且显式配置优先于框架默认值。矩阵就是把这句「必须决定」提前写下来的地方。

**负向用例集。** 断言「不能」的用例，不是「能」的用例。至少覆盖改资源 ID、换租户、去掉凭证、凭证过期、普通角色调管理接口。NIST SP 800-218（SSDF 1.1）把 PW.7「审查人类可读源码」和 PW.8「测试可执行代码」分成两个实践，就是因为看代码和跑程序是两件事；只交一份静态扫描报告，等于只做了前者。

**依赖清单 / SBOM。** NTIA 2021 年 7 月发布的《软件物料清单（SBOM）最低要素》给了七个基准字段：供应商名称、组件名称、组件版本、其他唯一标识符、依赖关系、SBOM 数据作者、时间戳；还要求机器可读（SPDX、CycloneDX、SWID 三种格式之一）、每个新版本重新生成。同一份报告里「实践和流程」部分有一项对甲方特别有用：**明确的未知**——依赖关系有没有穷举、哪里还不知道，要写出来，不许留白。外包方说不清某个组件从哪来，写「未知」也是一条结论，比空着强。API9:2023（Improper Inventory Management）讲的就是暴露的接口、旧版本、调试端点没人维护，清单本身就是这道防线。

## 三、不写代码也能做的四项核查

甲方不必读源码，下面四项都能在验收现场做完，且都能留下证据。

**换身份重放。** 准备两个普通账号加一个管理员账号，把演示过的每个带 ID 的接口重放一遍，只改 URL 或参数里的 ID，换成另一个账号的。断言是 403 或 404，不是 200。命令行就够：

```bash
# 用 A 的凭证，去取 B 的订单；期望被挡住
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $TOKEN_A" \
  "https://api.example.com/api/orders/$ORDER_ID_OF_B"
```

演示时这一步没人做，因为演示用的是「对的 ID」。把 ID 换掉，是整场验收里成本最低、收益最高的一分钟。

**要负向用例，别要「测试通过」。** 翻报告要能翻到断言 `assert r.status_code in (403, 404)` 的那几行，并且能在本地跑通。只写「安全性测试通过、未发现高危」而不附用例的报告，等于没有证据。

**单独点名管理类接口。** 从交付的路由表里把导出、批量操作、后台管理、重置密码这类接口挑出来，逐个问「普通用户调它会怎样」。API5:2023 说的管理功能与普通功能混淆，就是栽在这里。Authorization Cheat Sheet 要求权限在每一次请求上都校验，并建议用应用级的全局机制而不是每个方法各写一遍——所以还要追问一句：这个检查是全局挂上的，还是某个方法里手写了一次。

**干净机器复现构建。** 拿交付的源码加依赖清单，在一台没装过项目环境的机器上构建，产物和演示环境对不上，说明交付的源码不是线上跑的那份。SSDF 的 PS.3 要求归档并保护每个软件发行版所需的文件与支撑数据（完整性信息、来源信息），对应到验收就是这一条：能不能从零复现出同一个东西。

四项里第一项和第四项最容易被跳过，也最不容易被事后补做——一旦尾款付掉、外包团队解散，重放环境和干净机器都没了。

## 四、把核查点写进条款，别靠人情

验收是最后一次甲方手里有筹码的时点，动作要落在纸面上。

**尾款挂钩三件事**：交付清单齐、负向用例跑得通、干净机器复现构建通过。三样都过才签验收单，不是「功能演示通过」就签。

**留复验窗口。** 约定交付后一段时间内发现的安全类问题属于交付范围，不按新需求另行计费。没有这条，签完字等于免责，前面收的文件也就没了约束力。

**供应链义务写进合同附件。** 等保 2.0「服务供应商选择」要求明确整个服务供应链各方需履行的网络安全相关义务，正好用来约定：外包方引入的第三方组件要提供清单，组件出事要负责升级和告知。别只约束乙方自己写的代码。

**根因回写。** SSDF 的 RV.1 要求持续识别并确认漏洞，RV.3.1 是一句很实的动作：分析已识别漏洞的根因。落到合同就是：每查到一类越界访问，外包方交一份说明——授权矩阵哪一格没写、哪条负向用例没覆盖、哪次变更没触发重审——并补进交付物。缺了这条回路，同一个形态下个版本还会再来一次。

三个常见反模式，其实是同一个根因：**验收只确认「乙方说做完了」，没有留下「甲方能自己复核」的东西。**

- 只收源码不收证据。源码证明不了「换身份会怎样」，也证明不了线上跑的是不是这一份。
- 验收报告只写结论不写用例。结论无法复核，签字之后没人能推翻它。
- 把安全测试也交给同一家做。等于让被验收方自己出考卷、自己判卷。真要第三方，得由甲方委托、对甲方负责。

二阶影响也得说清楚：只补一次测试、不加矩阵和回写条款，下个版本接口一多，同类的漏洞会再回来，而且每次都得重新谈一次「这算不算新需求」。把要求写进交付物和合同，是把一次性博弈变成可重复的流程，这才是省事的地方。

## 五、一个下午能做完的最小动作

按这个顺序推，不需要甲方有人会写代码：

1. 收四份文件：设计文档与使用指南、源码及后门与隐蔽信道审查说明、测试验收方案与报告、上线前安全测试报告，外加一份逐项可勾的交付清单。
2. 让外包方从路由表导出带资源 ID 的接口清单，标出写操作、导出和管理类接口。
3. 挑最敏感的三个读接口做换身份重放，把返回码截图存档。
4. 要授权矩阵和负向用例集，作为验收附件写进合同，而不是邮件里一句「会注意的」。
5. 在干净机器上按依赖清单复现一次构建，记下是否一致。
6. 验收单上写清复验窗口、供应链义务和根因回写三条款。

做完这六步，手里就有了一批能涨能跌、能复核、能指定负责人的东西：带资源 ID 的接口里有多少写了归属条件、多少有负向用例、多少能复现构建。比「验收通过」四个字有用得多。

## 把清单固定下来

靠验收会上看一遍演示不牢，身份换了、数据换成多租户、接口加了，没人会回头把「换个人还能不能查到」重问一遍。

能机械判的那几项，交给每次都跑的检查更靠谱。带资源 ID 的查询有没有把归属条件和 ID 写进同一个条件里、写操作有没有取到当前用户身份、管理类接口有没有独立的认证依赖、新增路由有没有对应的负向用例。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事：7 大规则引擎把能从代码结构里读出来的形态逐条跑一遍。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
