2026 年 1 月，一个叫 Moltbook 的 AI 社交网络上线。创始人在公开场合说过一句话：他一行代码都没写，整个产品是跟 AI 聊出来的。

上线 72 小时内，一个配置错误的数据库把 150 万条 API 认证令牌和 3.5 万个邮箱地址暴露在公网上。

这个漏洞不高级。任何写过两年后端的人，做一次常规代码审查就能看出来。问题在于没有人审查——**整个应用是从对话里长出来的，没有"提交代码"这个动作，也就没有"审查代码"这个环节。**

这件事被反复引用，是因为它说明了一个结构性变化：审查这道工序，是被"AI 让你写得更快"这件事本身挤掉的。

## 先说清楚：AI 写的代码，问题不在"差"

说 AI 写的代码质量差，是不准确的。它写出来的东西往往比初级工程师更整洁：命名规范、结构清晰、注释齐全、类型标注一个不落。

真正的问题是另一件事：**它的一致性。**

美国三家大学（德克萨斯大学圣安东尼奥分校、俄克拉荷马大学、弗吉尼亚理工）在 USENIX Security 2025 上发表过一份测量：16 个模型、57.6 万段 Python 和 JavaScript 代码，**19.7% 的样本里至少引用了一个根本不存在的包名**。商业模型平均 5.2%，开源模型平均 21.7%，一共编造出 205,474 个不重复的假包名。

IOActive 2026 年的测试给出另一个数字：**31.6% 的 AI 生成代码样本是完全可利用的**——不是"理论上存在风险"，是拿过去就能打通。

Veracode 2026 年春季测了 100 多个模型，**45% 会直接引入 OWASP Top 10 里的漏洞**，其中跨站脚本失败率 86%，日志注入失败率 88%。

一篇 2026 年 7 月的形式化验证研究（3,500 个代码产物、7 个模型、用 Z3 求解器证明）给出 **55.8%**：超过一半的产物里存在至少一个能被形式化证明的漏洞。

把这些数字放在一起看，结论不是"AI 不行"，而是：**AI 写代码的失败模式是高度可预测的。** 它总在同样的几个地方出错，因为它的训练语料里那几处就是错的。

可预测，就意味着可以用一张固定清单去查。

## 这 6 个问题，按"出事了最疼"排序

### 一、换个人来调这个接口，还能拿到数据吗？

这是清单里最要命的一条，也是最难查的一条。

AI 生成接口时，几乎不会漏掉"有没有登录"。它很擅长加 `@login_required`、加 JWT 校验、加中间件。**它漏掉的是另一件事：这个登录的人，有没有权限碰这条数据。**

```python
@app.route("/api/orders/<int:order_id>")
@login_required
def get_order(order_id):
    order = Order.query.get(order_id)
    return jsonify(order.to_dict())
```

这个接口有登录校验。但它只检查了"你是谁"，没检查"这单是不是你的"。把 URL 里的 `order_id` 从 1001 改成 1002，就能看到别人的订单。

这类问题在安全领域叫**缺失授权校验**（Missing Authorization / 水平越权）。CWE 2025 年的 Top 25 里，"缺失授权"从第 9 位跳到了第 4 位——榜单变动的原因很直接：AI 生成的代码在批量制造它。

**30 秒怎么查：** 打开你自己的产品，用一个普通账号登录，然后把地址栏里所有数字 ID 逐个 +1、-1，看有没有哪个能打开不属于你的数据。查三个地方就够：详情页、编辑页、导出接口。

**为什么扫描器抓不到：** 漏洞在"没写的那行代码"里。没有关键字可匹配，没有危险函数可标记，代码语法完全正确、测试全部通过。要发现它，必须理解"这行 SQL 查出来的数据，应不应该给当前这个用户"——这是语义问题，不是模式问题。

### 二、密钥到底写在哪几个地方？

2025 年有研究团队用 900 条结构化提示去测 GitHub Copilot，从输出里提取出 **2,702 个硬编码凭据**，其中至少 200 个（约 7.4%）经确认是真实可利用的密钥。

GitGuardian 的数据是另一个角度：2025 年 GitHub 上新增了 **2,865 万个硬编码密钥**，其中 AI 服务相关的凭据泄露增长了 81%。

AI 犯这个错有个很具体的模式——它会给你留一句注释：

```python
STRIPE_KEY = "sk_test_51H8..."   # TODO: 上线前换成环境变量
DB_PASSWORD = "admin123"          # 生产环境请修改
```

这两行注释是它从训练语料里学来的。开源项目里到处都是这样的代码，模型学会了"这里应该有这么一个占位符"，但它不理解"占位符不能带进生产"。

**30 秒怎么查：**

```bash
# 在项目根目录跑，看当前代码里有没有
grep -rnE "(api[_-]?key|secret|password|token)\s*=\s*['\"][A-Za-z0-9_\-]{12,}" \
  --include="*.py" --include="*.js" --include="*.ts" --include="*.java" .
```

**更要命的是查历史记录。** 密钥从当前代码里删掉，不代表它没进过 git：

```bash
git log -p | grep -nE "(api[_-]?key|secret|password)\s*=\s*['\"][A-Za-z0-9_\-]{16,}"
```

如果查到了，光删代码没用——**得把那个密钥作废重发**，因为它已经在提交历史里躺着了，任何能 clone 这个仓库的人都能翻出来。

### 三、拼进 SQL 的那个变量，是从哪儿来的？

参数化查询这件事，AI 大部分时候做得对。但它会在两个地方破功。

第一个是排序和字段名，因为参数化查询传不了列名：

```python
# 危险：列名直接拼接
sort = request.args.get("sort", "created_at")
query = f"SELECT * FROM orders ORDER BY {sort}"
```

第二个是"它觉得这是内部值"：

```python
# 危险：看着像内部调用，其实 user_id 来自前端
user_id = request.json.get("user_id")
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")
```

**30 秒怎么查：** 搜项目里所有 `f"SELECT`、`+ " WHERE`、`% (` 的写法，以及 `.raw(`、`.extra(`、`order_by(` 后面跟着变量名的地方。ASP.NET 里搜 `FromSqlRaw`，Node 里搜 `query(` 后面接模板字符串。

判断标准很简单：**只要 SQL 字符串里有 `{}` 或 `+` 拼接的东西不是常量，就停下来看一眼。**

### 四、AI 让你装的那个包，真的存在吗？

这是这份清单里最新、也最少人知道的一条。

前面提到的那份 USENIX 研究里有个更关键的发现：研究者把已经产生过假包名的 500 条提示，每条又跑了 10 遍，**43% 的假包名在 10 次里全部重现**，58% 至少重现过一次。

这个数字决定了攻击能不能成立。如果假名字每次都随机，攻击者没法预判；但既然它会稳定重现，攻击者就可以提前把这个名字注册下来，等着。

这种攻击有个名字：**slopsquatting**（AI 幻觉 + 域名抢注的组合词）。

真实案例已经发生过了：

- 2025 年 12 月，npm 上一个叫 `metro-evaluator` 的包被植入了恶意代码，发了 4 个版本，5 天后被下架。这个名字是模型在被测时推荐过 10 次的那个。
- 一个叫 `react-codeshift` 的假包名（把真实存在的 `jscodeshift` 和 `react-codemod` 拼在一起），出现在 47 个生成文件里，扩散到 237 个以上的代码仓库。
- 2026 年有研究团队花约 496 美元，把 107 个 AI 幻觉出来的包名全部注册到 npm，观察了 6 个月：**35.2% 的安装量来自真实开发者**，大部分发生在上线后两周内。

**30 秒怎么查：** 装之前先问一句"这个包存在吗"。

```bash
# Python
pip index versions 包名

# Node
npm view 包名
```

如果查不到，别装。如果查得到但**发布者是最近注册的、只有 1 个版本、下载量个位数**，更别装。

**为什么这件事对 AI 编程特别危险：** 人类手打 `pip install` 的时候，多少会扫一眼名字。AI Agent 不会——它把装依赖当成任务的一部分，装完直接报"成功"，你根本不知道它装了什么。

### 五、日志里现在有什么？

这一条很多人会忽略，但 Veracode 的数据很直白：**AI 生成代码的日志注入失败率是 88%**，是所有类别里最高的。

AI 特别爱写"详细日志"，因为它觉得这样显得专业：

```python
logger.info(f"用户登录: {username}, 密码: {password}")
logger.info(f"请求参数: {request.args}")
logger.info(f"Token: {token}")
```

第一种直接把密码写进日志文件；第二、三种会把用户的 token、身份证号、手机号写进去。日志文件通常权限最松、保留最久、最容易被导出——**等于把敏感数据换了个地方存，还去掉了所有访问控制。**

日志注入是另一个方向的问题：用户输入里带一个换行符，就能伪造出一条看起来完全正常的日志，把攻击痕迹盖掉。

**30 秒怎么查：**

```bash
grep -rnE "logger\.[a-z]+\(.*(password|token|secret|request\.(args|form|json))" \
  --include="*.py" --include="*.js" --include="*.java" .
```

再看一眼日志的实际内容——日志文件里随便 grep 一下 `@`（邮箱）、`1[3-9]\d{9}`（手机号）、`Bearer`（令牌），看命中了多少。

### 六、出错的时候，它对外说了什么？

```python
app.run(debug=True)          # 上线了还开着调试模式
```

```python
@app.errorhandler(Exception)
def handle(e):
    return jsonify({"error": str(e), "trace": traceback.format_exc()}), 500
```

这两种写法在 AI 生成的代码里都很常见，因为它们在开发时"好用"——报错信息全，排查快。上线之后就变成了给攻击者递地图：文件路径、框架版本、数据库表名、SQL 语句，全在里面。

**30 秒怎么查：** 随便找一个会报错的接口，故意传一个非法参数，看返回的是不是一句人话（"参数格式错误"），还是一整段堆栈。

## 六条查完，还剩一个真问题

上面这六条，一、二、三、五、六都能靠 grep 和自己点几下查出来。**只有第一条不行。**

因为越权漏洞不在代码里，在"应该存在但不存在"的那部分里。它没有特征、没有关键字、没有危险函数。你没法用正则去搜"这里少了一行权限判断"。

这也是为什么传统代码扫描器在这件事上结构性吃力——它们的工作方式是"匹配已知的危险模式"，而这里的问题是"缺失"。缺失是没有模式的。

更现实的问题是量。当 AI 把每天的代码产出提高三到四倍，靠人肉过一遍这六条清单是不现实的。IBM 的研究提到，AI 辅助的开发者提交量是同事的三倍以上，但集中在更少、更大的 PR 里——**这恰恰是最难审的形态。**

所以清单的价值不在于"每天照着做一遍"，而在于：**知道该查什么，然后让机器去查能查的，人只看机器查不了的那部分。**

## 一个可以马上做的动作

如果你手上正有一段 AI 写的代码，不确定上面六条里踩了几条，可以粘进来跑一遍，几秒出结果，不用注册：

**https://xinpect.xingwangzhineng.com/try**

**哪几条单段代码就能查：** 二（硬编码密钥）、三（注入）、五（日志）、六（报错信息泄露）——这四条粘一个文件就够，规则能直接命中。

**哪几条必须给整体：** 一（越权）和四（依赖）。越权要判断"这条数据属于谁"，得看数据模型和权限层；依赖要看你实际装了什么，得看锁文件。这两条只给一个接口文件，任何工具都判断不了。

我们在这两条上花的力气最多——数据流追踪和缺失约束识别，就是处理"代码里什么都没写错，但逻辑上少了一步"的。但要让它生效，得喂给它足够的上下文。

扫描报告会把问题定位到具体文件和行号，并给修复建议。**报告不是重点，重点是你能拿着它去改。**
