先看一段代码。这是一个考勤系统查记录的接口，AI 生成的，能跑、能过测试、能上线。

```python
@app.route("/api/attendance/<int:user_id>")
@login_required
def get_attendance(user_id):
    records = Attendance.query.filter_by(user_id=user_id).all()
    return jsonify([r.to_dict() for r in records])
```

有问题吗？

看一眼觉得挺规范的：有路由，有登录校验，有参数类型限制，查询用了 ORM 不是拼接 SQL。代码评审大概率会放过。

但它有一个致命的缺陷：**`user_id` 是从 URL 里来的，代码没检查这个 id 是不是当前登录用户自己的。**

也就是说，任何一个登录用户，把浏览器地址栏里的数字从 `1024` 改成 `1025`，就能拿到同事的考勤记录。改成管理员的 id，拿到管理员的。

这类问题叫**水平越权**（也叫缺失授权校验、IDOR）。OWASP 分类里属于 Broken Access Control，常年排第一。

---

## 为什么测试抓不到

因为这个接口的测试，一定是这么写的：

```python
def test_get_my_attendance():
    login_as(user_a)
    resp = client.get("/api/attendance/%d" % user_a.id)
    assert resp.status_code == 200
    assert len(resp.json) > 0
```

**测试验证的是"我能查到我自己的"。没有人写"我查不到别人的"。**

这不是测试写得不用心，这是测试的天然盲区：你在写测试的时候，脑子里想的是"功能对不对"，而越权不是功能问题——功能完全正确，它只是**多给了一份权限**。

单元测试是断言"应该发生的发生了"，越权是"不应该发生的也发生了"。前者是加法，后者是减法。**你没有写那个断言，就永远不会发现它。**

---

## 为什么扫描器也抓不到

这才是关键，也是很多人想不通的地方：这行代码里，没有任何"可疑的东西"。

- 没有字符串拼接 SQL，所以 SQL 注入规则不触发
- 没有 `eval`、没有 `exec`，所以代码执行规则不触发
- 没有硬编码密钥，所以密钥检测不触发
- 参数做了 `int` 类型约束，所以类型校验规则反而给绿灯

**漏洞不在写了的那几行里，在没有写的那一行里。**

传统静态扫描器的工作方式是：拿已知漏洞的特征去匹配代码。比如看到 `"SELECT * FROM users WHERE id=" + user_id` 就报 SQL 注入——因为有明显的危险特征。

但"少写了一行权限判断"，特征是什么？**没有特征。** 它跟一段完全正确的、安全的代码，在前几行长得一模一样。

你要判断这件事，必须回答一个问题：

> 这个用户，有没有权利访问这条数据？

而这个问题，答案不在当前这个函数里——它在用户表、角色表、数据归属关系、业务规则里。**扫描器必须跨文件追踪数据流，还要理解"授权"这件事在这个系统里是怎么表达的**，才可能判断出来。

光靠正则和关键词，结构上做不到。

---

## 这不是个案，榜单已经说明了

CWE Top 25 的 2025 年榜单里，**Missing Authorization（缺失授权校验）从第 9 名跳到第 4 名**，是上升最猛的类别之一。

而这个上升的时间线，跟 AI 编程工具普及的时间线高度重合。这不是巧合。

---

## AI 为什么特别容易犯这个错

因为 AI 学的是"能跑通的代码"，不是"能上线的代码"。

它的训练语料里，大量是教程、demo、示例项目。而教程代码为了让读者看清主逻辑，几乎都会**把权限校验、边界检查、错误处理全砍掉**——因为那些东西跟"讲清楚这个功能怎么实现"无关，还会让示例变长。

比如一个教程讲"如何做一个用户资料接口"，它大概率长这样：

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return db.query(User).get(user_id)
```

干净、清晰、能跑。这个示例被复制了几百万次，进了语料库，也进了 AI 的脑子里。

**AI 学到的是：查数据，按 id 查，返回。**

它不知道真实系统里，这中间必须夹一层"这个 id 归不归你"的判断——因为教程里从来没写过。

还有第二个原因：AI 是按文件生成代码的。你让它写一个查询接口，它就把这个接口写对。**而"这个接口在整条权限链路上的位置"，它看不到。** 权限校验往往横跨认证、用户体系、数据归属三个模块，任何单文件视角都会把它漏掉。

---

## 正确的检查方式长什么样

要抓这一类问题，工具必须做三件事，缺一不可：

**第一，跨文件追踪数据流。**

从 `user_id` 这个参数进来到最后落到查询条件上，中间经过了哪些处理？有没有跟当前登录用户做过比对？这一步是数据流分析，不是文本匹配。

**第二，识别"授权模式"。**

同一个团队里，权限校验通常有固定写法——可能是装饰器，可能是中间件，可能是显式判断 `if resource.owner_id != current_user.id`。工具要先学会这个系统里"授权长什么样"，才能判断某一处**缺了**它。

**第三，能容忍"看不见的那部分"。**

如果授权逻辑放在网关层或者框架拦截器里，单个函数里本来就不该有。工具得知道哪些是"在别处已经做了"，不能一见到没有就报。**这一步决定了误报率能不能压下来**——报一堆假问题，等于没做。

---

## 你自己可以马上做的三件事

不用等工具，今天就能查：

**1. 把所有带 id 参数的接口列出来。**

`/api/xxx/<id>`、`?id=123`、POST body 里的 `user_id`、`order_id`、`tenant_id`——凡是客户端能指定的 id，全部列成一张表。

**2. 逐个回答：这个 id 归谁？**

对每一个，问一句"如果我是用户 A，我把这个 id 改成用户 B 的，会怎样"。答不上来的，就是风险点。

**3. 在测试里加反向断言。**

每条功能测试旁边，加一条"用别人的 id 应该返回 403"。这一条断言的成本是 5 分钟，能挡住这类问题 90% 的复发。

```python
def test_cannot_read_others_attendance():
    login_as(user_a)
    resp = client.get("/api/attendance/%d" % user_b.id)
    assert resp.status_code == 403   # 这一行是防线
```

## 最后

用 AI 写代码这件事本身没有问题，它确实快。但有一件事必须记住：

**AI 交付的是"功能"，不是"安全边界"。** 边界是业务规则，只有你知道谁该看什么。

所以在提交前，那道检查不能省——而且检查的方式得对：不是问"有没有明显的危险代码"，而是问"**这段代码允许谁、访问什么**"。

我们做煋鉴，主要精力就放在这一类问题上：**不看有没有危险特征，看有没有缺失的约束。** 越权、缺失校验、跨租户数据访问，这些在代码里"什么都没写"的漏洞，是我们和其他扫描思路最大的区别。

想拿自己的代码试一遍：

`xinpect.xingwangzhineng.com` — 网页上传就能扫，不用装任何东西。

**一句实话，免得你白试：** 贴一段代码进来，能查出"路由参数直接拿去查库、中间没有权限校验"这类形态——识别出来不难，难的是定性。判断"这条数据到底该不该给他"，得知道数据模型长什么样、权限写在哪一层，这些信息往往不在同一个文件里。

所以单段代码给的是线索，整个项目才能定论。这也正是这类问题难查的原因：**它不在某一行代码里，在整个结构里。**
