# AI写代码最容易写错的权限校验：5 种接口写法，只有一种挡住了越权漏洞

给模型一句「用 FastAPI 写个订单查询接口，按订单 ID 返回详情」，拿回来的代码通常很体面：路径参数有类型、数据库用了参数化查询、查不到返回 404、异常有包装、日志也打了。复制到项目里跑一遍，自己账号查自己订单，返回正确。评审看一眼，没问题，合了。

上线两个月，运营发现换个订单编号就能看到别家公司的金额和收货地址。回头翻那段代码，每一行都写得对，只是少了一句：这个订单是不是当前登录人的。

这类问题不叫写错了，叫**没写**。语法错误会让接口跑不起来，缺一行归属判断不会有任何报错，也不会让任何一条功能用例变红。OWASP API Security Top 10 2023 把 API1:2023（Broken Object Level Authorization，对象级授权失效）排在第一位，官方描述里那句话很直白：**凡是拿用户提供的 ID 去访问数据源的功能，都要考虑对象级授权检查**。生成式代码擅长把「看得见的字段」用起来，而这条判断不在字段里，只在业务规则里。

## 一、认证、授权、归属，是三件不同的事

很多稿子把这三件事混成一个词，代码里也就混成一句 `if not user: 401`。拆开看：

- **认证**回答「你是谁」：令牌有效、会话没过期。
- **功能级授权**回答「你能不能调这个功能」：普通用户能不能走导出接口。OWASP API5:2023（Broken Function Level Authorization）管的就是这类。
- **对象级授权**回答「这条数据能不能给你」：订单 102 存在、你也有查订单的权限，但它是别人的。

MITRE 的 CWE 里对应三条：CWE-862（Missing Authorization，压根没做授权检查）、CWE-863（Incorrect Authorization，做了但判错）、CWE-639（Authorization Bypass Through User-Controlled Key，靠改标识就能绕过）。CWE-639 的定义几乎就是上面那个改订单编号的场景，别名直接写着 IDOR 与 BOLA。

一句 `if not user: 401` 只解决了第一件。第二件和第三件都得单独写，而且第三件必须落在**每一次数据访问**上，不是落在路由入口就算完。

## 二、把 5 类常见写法摆到同一张桌子上

这里不点名任何工具，也不做跑分排名。不同模型、不同提示词生成的代码千差万别，但落到权限校验上，翻来覆去就是下面这几种形态。把形态抽出来做成可复现的最小实验，判定结果能自己重算，比记「某某工具更靠谱」有用得多。

**场景**：内存里三条订单，当前用户是 `u1`、租户 `t1`、角色 `user`。

| 订单 ID | 租户 | 归属用户 | 金额 |
|---|---|---|---|
| 101 | t1 | u1 | 120 |
| 102 | t1 | u2 | 340 |
| 201 | t2 | u3 | 560 |

**6 条请求**：1 条应该放行（本人查本人），5 条应该拒绝。判据只有一句——**是否把当前用户或当前租户以外的数据交出去了**。

| 编号 | 请求 | 期望 |
|---|---|---|
| C1 | 未登录，查 101 | 拒绝 |
| C2 | 登录为 u1，查本人的 101 | 放行 |
| C3 | 登录为 u1，查同租户他人的 102 | 拒绝 |
| C4 | 登录为 u1，查跨租户的 201 | 拒绝 |
| C5 | 把请求里的 owner 参数改成目标值 u2，查 102 | 拒绝 |
| C6 | 普通用户调用管理导出接口 | 拒绝 |

5 种写法分别是：只按 ID 查；只验登录；归属条件取自请求参数；只验能力名；服务端取身份、归属条件与 ID 进同一个查询。核心代码（精简版，完整可跑脚本见文末溯源段）：

```python
ORDERS = [Order(101, "t1", "u1", 120),
          Order(102, "t1", "u2", 340),
          Order(201, "t2", "u3", 560)]

def v1_only_id(r):
    if r.is_admin_api:
        return list(ORDERS)
    return by_id(r.order_id)

def v2_login_only(r):
    if r.user is None:
        return None
    if r.is_admin_api:
        return list(ORDERS)
    return by_id(r.order_id)

def v3_owner_from_request(r):
    if r.user is None:
        return None
    if r.is_admin_api:
        return list(ORDERS)
    o = by_id(r.order_id)
    if o and o.owner_id == r.owner_param:
        return o
    return None

def v4_scope_only(r):
    if r.user is None:
        return None
    if r.role not in ("user", "admin"):
        return None
    if r.is_admin_api:
        return list(ORDERS)
    return by_id(r.order_id)

def v5_server_side_ownership(r):
    if r.user is None:
        return None
    if r.is_admin_api:
        if r.role != "admin":
            return None
        return [o for o in ORDERS if o.tenant_id == r.tenant]
    o = by_id(r.order_id)
    if o and o.tenant_id == r.tenant and o.owner_id == r.user:
        return o
    return None
```

注意 V3：它确实写了 `owner_id` 判断，看起来最像「有做权限」。但那个值来自请求参数，是调用方自己填的。C5 就是把参数改成目标的归属值，判断立刻反过来替攻击者服务。

## 三、实跑结果

6 条请求逐个跑完，结果是这样：

| 写法 | 应拒绝的 5 条挡住几条 | 本人查询 | C5 篡改参数 | C6 管理导出 |
|---|---|---|---|---|
| V1 只按 ID 查 | 0 / 5 | 放行 | 漏出 | 漏出 |
| V2 只验登录 | 1 / 5 | 放行 | 漏出 | 漏出 |
| V3 归属取自请求参数 | 3 / 5 | 放行 | 漏出 | 漏出 |
| V4 只验能力名 | 1 / 5 | 放行 | 漏出 | 漏出 |
| V5 服务端归属同查询 | 5 / 5 | 放行 | 挡住 | 挡住 |

**V1 到 V4 在「本人查本人」这条上全部通过。** 这正是问题最难被发现的地方：功能测试、联调、演示、验收走的全是 C2，谁来都绿。5 条该拒的请求里，V2 和 V4 只挡住了未登录那一条，等于把「登录了」当成了「有权看全部」。V4 尤其值得说：`orders:read` 这类能力名回答的是功能级问题，不是对象级问题，有权限读订单，不等于有权限读**这一条**订单。

**V3 是最有迷惑性的一种。** 5 条里挡住 3 条，代码里还明晃晃写着 `owner_id` 校验，评审容易放过。可只要攻击者把请求里的归属值改成目标数据的归属值，判断就从「拦住他」变成「替他确认」。归属条件必须来自服务端会话，不能来自请求体，这是没有例外的。CWE-639 给的缓解建议也是这一条：用于查找记录的键不能被外部控制，或者服务端能发现它被改过。

**V5 全过，但它不是终点。** 它做对了两件事：身份从会话取，归属条件与资源 ID 落在同一个查询里；管理导出单独判角色，且把范围收在当前租户内。OWASP Authorization Cheat Sheet 强调的「默认拒绝、在服务端强制校验」，落到这里就是这两行。ASVS 5.0 的 V8 访问控制章节也把功能级与数据级分开要求，不是一道 `if` 能覆盖的。

还有一类 V5 没覆盖：对象属性级。API3:2023（Broken Object Property Level Authorization）说的是，就算记录本身有权读，响应里也不该把 `owner_id`、手机号、内部备注整块吐出去；反过来，写接口也不该允许请求体带 `status`、`tenant_id` 这类字段直接改。这属于同一条数据上的第二次判断，代码审查里得单独列一项。

## 四、把判据写成能机械核对的清单

「写接口时记得加权限」靠不住，人会忘，模型也不会自己补。能交给检查的是下面这些**从代码结构里读得出来的形态**：

1. **带资源 ID 的查询，归属条件与 ID 是否在同一个条件里。** 先按 ID 查出来再在内存里 `if` 判归属，也能挡住，但批量接口、缓存层、后续加的字段很容易绕开这层。写进同一个查询最稳。
2. **当前用户身份从哪里来。** 出现 `owner_id = query.owner_id`、`request.user_id`、请求体里的 `tenant_id` 当归属条件，一律判不合格。只认会话或框架注入的当前用户。
3. **每个带 ID 的路由有没有负向用例。** 不是「返回 200 且字段齐全」，而是换一个用户、换一个租户、同一身份重放，期望 403 或 404。C3、C4 这两条用例缺一条都不算过。
4. **管理接口有没有独立的角色依赖。** 导出、批量改状态、用户管理这类路由，不能和查询接口共用同一个 `current_user` 依赖。API5:2023 的高发点就是管理与常规功能混在一起。
5. **写操作有没有重新取当前用户。** 改地址、改状态、删记录，别复用读接口那次判断，尤其别复用前端传回来的对象。CWE-863 里相当一部分就是「判了，但判的是旧对象」。
6. **响应字段有没有做属性级过滤。** 返回模型直接 `dict(row)` 是最常见的写法，也最容易把不该给的字段一起带出去。
7. **新增路由有没有进清单。** API9:2023 讲的是存量管理：暴露的端点比想象中多，废弃版本、调试路由、临时接口都在。接口清单不同步，前面 6 条写得再好也会有漏网的。

这份清单的价值在于**它不要求评审者当天状态好**。每一行都能对着代码或测试文件打勾，也能写进提交前的自动检查。业务上「谁允许看谁的数据」得团队自己定义，机器替不了；但「归属条件有没有和 ID 写在一起」这种形态，机器能天天盯。

## 五、接生成代码之前，先跑这 6 条

把上面的用例做成负向测试，成本很低：两个租户、三个账号、一组固定 ID，一个测试文件就能装下。接 AI 生成的接口代码时，先跑这 6 条再合，比上线后翻事故记录便宜得多。

有三件事别做。别只跑正向用例，功能全绿和「别人拿不到」是两回事；别拿「本次没发现问题」当成「代码很干净」，覆盖面有限的检查给不出这个结论；别把安全检查全押在评审时的记忆上，人会疲，模型会顺着提示词走，只有写进测试和提交检查的动作每次都会发生。

回到开头那句：模型把能看见的字段都安排妥当了，缺的那行判断不在任何字段里。把「这条数据归谁」写进需求，把归属条件写进查询，把换身份重放写进测试，这件事才算做完。

## 把清单固定下来

AI 写接口时会把看得见的字段都安排妥当，唯独「这条数据归谁」得有人明确写进需求，写完还得换一个身份重放一次。

能机械判的那几项，交给每次都跑的检查更靠谱。带资源 ID 的查询有没有把归属条件和 ID 写进同一个条件、身份是不是从服务端会话取而不是从请求参数取、管理接口有没有独立的角色依赖、新增路由有没有换身份重放的负向用例。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事：7 大规则引擎把能从代码结构里读出来的形态逐条跑一遍。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
