# SonarQube 能查什么、查不到什么：代码审查里最容易被漏掉的越权漏洞

一个很常见的复盘现场：团队把静态扫描接进了 CI，质量门禁全绿，PR 上再没有红叉，代码规范和技术债指标都好看。几个月后线上出了一次越权——把请求里的订单号换成别人的，接口照样返回完整明细。复盘会上有人问，扫描为什么没报？

答案不是「规则库不够大」。这类缺陷的形状，压根不匹配静态分析的判据。把边界讲清楚比换工具更有用：它擅长什么、哪一类必须另开一条线、以及为什么质量门禁绿不等于可以上线。下面按官方能力和代码形态说实话，不吹也不踩。

## 一、先把擅长的事说清楚

静态分析拿到的输入是源码，判断依据无非两类：规则匹配，以及沿着数据流追踪。在这个范围内，SonarQube 做得相当扎实，主要有这么几层。

**规范与可维护性。** 命名、重复代码、圈复杂度、过长函数、注释与结构、单元测试覆盖率展示、技术债度量。这一层是它的传统主场，也是「Clean as You Code」那套方法论能落地的原因——卡住新增代码，比要求全仓历史清零现实得多。

**确定性的 Bug。** 空指针解引用、资源未关闭、条件恒真、异常被吞、部分并发误用。这类问题在源码里有稳定形态，规则能指到具体行号。

**注入类问题。** 商业版本提供的污点分析（taint analysis）会把不可信输入当作污染源，从它进入应用的位置一路追到被使用的危险操作，跨函数、跨文件地还原整条路径，能覆盖 SQL 注入、XSS、SSRF、命令注入、反序列化、路径穿越等。官方方案页列出的支持语言包括 Java、C#、JavaScript、TypeScript、Python、PHP、Kotlin、Go、VB.NET，并说明这种跨文件追踪是为了提高结果精度。企业级还有安全引擎自定义配置，能把追踪延伸到第三方库与自有代码的交互。

**密钥与配置。** 硬编码口令、云凭证这类字面量检测，以及 Terraform、CloudFormation、Dockerfile、Kubernetes 清单里的安全配置检查，比如传输是否加密、存储是否公开。

有一点必须先说明白，否则下面所有结论都会读歪：**社区开源版与商业版不是同一套能力**。社区版的能力清单是「基础漏洞检测 + 安全热点复核 + 基础密钥检测 + 质量度量」，污点分析属于 Developer Edition 及以上。所以在社区版上看到「注入类没有告警」，只能说明这个版本的规则集没有报，不能推出代码里没有注入。

## 二、最容易被误读的一个设计：安全热点不是漏洞结论

官方对 Security Hotspot 的定义很克制：它高亮的是「对安全敏感的一段代码」，整体应用的安全性未必受影响，**需要开发者结合上下文复核，再决定要不要修**。而 Vulnerability 是已经确认影响应用安全的问题，需要立即修。两者差的不是严重程度，是「是否还需要人来定性」。

热点有独立的状态流：To review → Acknowledged（确认有风险、处理方式待定）、Fixed（已修）、Safe（复核后判断无需改动）。注意 Safe 的含义是「人看过、结论是不用改」，不是「工具证明这里没问题」。官方举的例子是 RSPEC-2092，关于 cookie 的 Secure 标记：HTTPS 本身已经防住中间人，Secure 只是额外一层；如果这个 cookie 本来就要在非 HTTPS 场景发送，那不改也合理。判断依据是部署方式和威胁模型，源码里读不出来。

于是有两种很常见的误用：把热点批量标成 Safe 让面板清零；或者看到「安全问题 0 个」就当成安全验收通过。前者是人为清空待办，后者是把「已确认的问题」当成了「全部风险」。

还有个版本差异值得记一笔：官方 2026.3 的安全报告文档说明，部分热点规则正在逐步改为直接报告为漏洞，界面术语也因模式而异（Standard Experience 叫 Security Vulnerability，MQR Mode 叫 Security）。所以不同版本看到的数量和名称对不上，先确认自己用的是哪一版，别拿旧截图对账。

## 三、查不到的三类，越权排第一

看两段同一个接口的写法。第一段能被污点分析抓到：

```python
@app.get("/api/orders/detail")
def order_detail(order_id: str, db: Session = Depends(get_db)):
    sql = "SELECT * FROM orders WHERE id = '%s'" % order_id
    return db.execute(sql).fetchall()
```

污染源是请求参数，危险操作是 SQL 执行，中间是一条清晰可追的路径。第二段抓不到：

```python
@app.get("/api/orders/detail")
def order_detail(order_id: int, db: Session = Depends(get_db)):
    return db.query(Order).filter(Order.id == order_id).first()
```

这里没有脏数据。`order_id` 是合法整数，ORM 查询是参数化的，没有拼接，没有污染源流向危险操作的路径。工具能看见的每一行都是对的。缺的是 `Order.user_id == current_user.id` 这一行——而「当前用户是谁」「这张订单归谁」是业务定义，不写在源码里，也不写在需求写得不够细的那些接口文档里。扫描器不知道你的权限模型，自然无从判断这一行该不该存在。

把边界摊开看，能判和不能判的分界其实很整齐：

| 问题形态 | 能否从源码单独判定 | 判据落在哪 |
|---|---|---|
| 拼接 SQL | 能 | 存在请求参数到执行点的污染路径 |
| 硬编码口令 | 能 | 字面量特征与变量命名 |
| cookie 未设 Secure | 能标记，需复核 | 取决于部署与威胁模型 |
| 资源 ID 缺归属条件 | 不能 | 「谁能看谁的数据」是业务定义 |
| 网关是否校验内部调用 | 不能 | 信息分散在多个仓库与部署配置 |
| 检查与使用之间状态被改 | 不能 | 需要运行时的时间轴 |

具体归成三类。

**第一类，业务授权语义。** 谁能看哪条数据、谁能改哪个状态、哪些操作需要二次认证。对应 CWE-862 缺失授权、CWE-639 用户可控键绕过授权（也就是常说的 IDOR）、CWE-306 关键功能缺少认证。OWASP API Security Top 10 把对象级授权失效列在 API1，长期居首，本身就说明工具链和这类问题之间存在结构性空隙——不是某家工具没做好，是这一类问题的判据不在源码层。

**第二类，跨服务与跨层的信任边界。** 单仓库静态分析只看得见一个仓库。网关有没有拦、服务间调用有没有带身份、内部接口是不是默认信任上游，这些信息分散在网关配置、部署清单和另外几个仓库。在某个服务里「从请求头读 user_id」完全合规，但上游谁能伪造这个请求头，是另一层的事，静态分析推不出来。

**第三类，依赖运行时状态的时序问题。** 检查与使用之间数据被改（TOCTOU）、并发下的余额与库存扣减、权限撤销后旧令牌是否立即失效。静态分析不连数据库、不发请求、不推进时间轴，这类结论无法从源码单独得出。

补一句公道话，免得读成「这工具不行」：它有相当程度的框架感知能力，能识别不少安全敏感 API，商业版也支持自定义安全引擎配置。但「这个资源该不该给这个用户」始终由业务定义，不是语法事实。这一层靠规则天然推不出来，跟产品好坏无关。

## 四、根因：找「写错的行」和找「没写的行」是两件事

静态分析的判据是「写出来的代码里有没有错误形态」。越权的判据是「这个接口本该具备的约束是否齐备」。前者做模式匹配，后者做完整性检查。两种判据不共用一套数据结构，把它们塞进同一个质量门禁，结果必然是门禁绿、风险还在。

更关键的是，缺席型缺陷在改动记录里也是看不见的。代码评审看的是这次改了哪些行，功能测试跑的是照着需求写的断言，两者都以「写了的代码」为对象。一行根本不存在的归属条件，不会出现在任何 diff 里，也不会让任何一条断言变红。所以这类问题不会自己冒出来，得有人专门去点名。

落到流程上，四件事就够：

1. **把两层分开写。** CI 里的质量门禁只管规范、确定性 Bug、注入与密钥；上线前的安全验收另开一张接口级清单。别让「门禁通过」在流程文档里等价于「可以发布」。
2. **热点复核留痕。** 状态、复核人、判断理由都记下来，禁止批量置为 Safe。面板清零不是目标，复核覆盖才是。
3. **清单要指到行号。** 每个写操作接口问一句当前用户身份从哪来、落在哪一行；凡是拿资源 ID 查数据的，归属条件必须和 ID 出现在同一个查询条件里；管理类接口单独确认认证依赖，不假设「网关已经挡住了」。答「应该有吧」等于没有。
4. **按实际使用的版本下结论。** 用社区版就别把「注入类零告警」写进安全结论；想让机器判缺席，判据得从「匹配错误模式」换成「检查每个接口是否具备身份依赖与归属条件」。

工具放在它擅长的那一层，需要理解业务的那一层单独列成清单。门禁绿是过程信号，不是上线结论。

## 六、把清单固定下来

静态扫描守的是「写错的行」，越权缺的是「没写的行」。门禁全绿、功能正常、改动干净的时候，没人会想起来念一句「这个接口该先确认是谁在调用」。

能机械判的那几项，交给每次都跑的检查更靠谱。每个写操作接口有没有当前用户身份、带资源 ID 的查询有没有把归属条件和 ID 写在同一个条件里、管理类接口有没有独立的认证依赖、first() 与 get() 的返回值用之前有没有判空。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
