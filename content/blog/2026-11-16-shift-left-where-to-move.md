# 安全左移到底该移到哪：从需求评审到上线，代码审查每个节点该留下的越权漏洞证据

「我们已经在 CI 里加了扫描，安全左移做完了。」这句话在评审会上很常见，也很容易验证它站不住：问一句「谁能读别人的工单附件，这条结论写在哪份文件里」，通常没人答得上来。工具跑在流水线里，规则却从来没被写下来过。

左移这个词被用坏了。它原本说的是把安全决策放到还能改变结果的时点，不是把同一台扫描器往前挪几步。判断有没有真的左移，只看一件事：这个节点有没有产出一个下游能拿去核查的东西——一份矩阵、一条会变红的测试、一个指到行号的结论。没有产物，就只是提前开了一次会。

## 一、把扫描提前，为什么还是拦不住越权

代码里的问题大致分三类，能被自动化处理的只有第一类。

**形态可判的。** SQL 字符串拼接、硬编码凭证、依赖版本、明文传输、异常被吞掉。这些能直接从代码结构里读出来，越早跑越省事，工具确实该进流水线。

**语义要先定义的。** 某个角色能不能读某个资源、跨租户能不能访问、哪些字段只允许特定角色改。代码里「没写检查」不等于「业务上不允许」，工具不知道「允许」长什么样。看一个带两层资源 ID 的下载接口：

```python
@app.get("/api/tickets/{ticket_id}/attachments/{file_id}")
def download(ticket_id: int, file_id: int, db: Session = Depends(get_db)):
    return db.query(Attachment).filter(Attachment.id == file_id).first()
```

这一行没有语法错误：参数声明成整数、ORM 查询是参数化的、没有拼接、没有异常。缺的是一句业务判断——这个附件是不是这个工单的、这个工单是不是这个人能看的。工具能查出「没有取当前用户身份」，查不出「该不该给」，因为后者从来没在任何文件里被定义过。补完之后两层归属都得落进查询条件：

```python
@app.get("/api/tickets/{ticket_id}/attachments/{file_id}")
def download(ticket_id: int, file_id: int,
             user: User = Depends(current_user),
             db: Session = Depends(get_db)):
    ticket = (db.query(Ticket)
                .filter(Ticket.id == ticket_id, Ticket.owner_id == user.id)
                .first())
    if ticket is None:
        raise HTTPException(status_code=404)
    return (db.query(Attachment)
              .filter(Attachment.id == file_id,
                      Attachment.ticket_id == ticket.id)
              .first())
```

外层校验工单归属，内层把附件绑回工单。只做第一层，改一下 `file_id` 就能拿到别人工单里的附件——这类形态在真实系统里比单层 ID 更常见，因为第二层资源往往被当成「反正外层已经拦过了」。

**运行时才看得见的。** 权限变更后是否立即生效、制品有没有被替换、配置有没有漂移、日志能不能回答「谁读了谁的数据」。这些只能在部署和运营侧验证，跟代码扫描不在同一个平面。

NIST SP 800-218（SSDF 1.1，2022 年 2 月发布）的摘要把目标写成三件事：减少已发布软件中的漏洞数量、降低未被发现或未被处理的漏洞被利用后的影响、从根因上减少未来复发。三件事对应三个不同位置，一套工具包办不了。同一份文档在 PO.3「实施支撑工具链」里给自动化的定位是：减少人力投入、提高准确性、可复现性、可用性和全面性，并提供记录与证明这些实践确实执行过的途径。自动化在这里是**证据生产器**，不是决策者。

所以左移真正要移的是决策点：把「谁允许访问什么」这句结论，从上线后的猜测，挪到需求评审里写成文件；再让后面每个节点拿这份文件去核对。

## 二、六个节点，每个节点交出什么

下面按生命周期顺序拆。每段只写三件事：该产出的文件、能核查的判据、最容易漏的地方。

### 节点 1 · 需求评审：产出授权矩阵和信任边界

OWASP SAMM 2.0 把软件安全拆成五个业务功能、十五项实践，其中「设计」这一块下的三项正是威胁评估、安全需求、安全架构。安全需求被排在设计和编码之前，不是测试阶段补的一页文档。ASVS 5.0 的 V8 授权章节把控制目标写得更直白：授权规则要形成文档（包含决策因素和环境上下文），使用者只能访问其权限允许的资源。8.1.1 要求文档定义函数级与数据级的访问限制规则，8.2.2 要求数据级限制以缓解 IDOR 与 BOLA，8.4.1 要求多租户应用有跨租户控制。

产物可以很小，但每一格都得是结论：

```text
资源          角色          读    写    导出   判据所在位置
工单附件      提交人        √     ×     ×     authz/matrix.md#att-1
工单附件      处理人        √     √     ×     authz/matrix.md#att-2
工单附件      同租户其他人  ×     ×     ×     默认拒绝
```

这张表最容易出的问题是写得太抽象。「只有授权用户能访问」等于没写。一格一个结论，带上资源、角色、操作，以及这个结论落在哪个文件的哪一段。表里没写的操作按拒绝处理——OWASP Authorization Cheat Sheet 对这点的说法是：应用在收到访问请求时不能保持中立，必须做出允许或拒绝的决定；显式配置优先于依赖框架或库的默认值，因为第三方逻辑会随版本变化。

### 节点 2 · 设计评审：产出接口清单、威胁模型、默认拒绝策略

SSDF 的 PW.1 要求识别并评估安全需求、确定软件运行中可能面对的风险以及设计架构该如何缓解，并对任何放宽或豁免给出基于风险的理由。PW.2 更进一步：由未参与设计的人，或工具链中的自动化流程，复核设计是否满足安全要求与风险约束。注意复核对象是**设计**，那会儿代码还没写。

接口清单从路由表自动导出，标出三类：带资源 ID 的、写操作、管理类接口。清单生成出来，不是靠人回忆。威胁模型沿着这张清单走，每个入口都问一次「换了身份会怎样」。

设计阶段最常见的漏点：正常路径画得很细，拒绝路径没人画。攻击者走的恰恰是那条没画的路径。

### 节点 3 · 编码：把结论写进同一个查询条件

前面那段 Python 就是这一节点的产物：归属条件和资源 ID 落在同一个查询里，两层资源逐层绑定。另一条硬规矩是检查的位置。Cheat Sheet 要求权限在**每一次请求**上都要校验，不管请求来自页面脚本、服务端还是别的入口；并建议用全局、应用级的机制（Java 过滤器、Django 中间件、.NET Core 过滤器、Laravel 中间件）而不是逐个方法各写一遍。ASVS 8.3.1 说明原因：授权必须在可信的服务层执行，不能依赖客户端能改动的控件，前端判断只改善体验，不决定放行。

要分清两件事：全局中间件解决「检查有没有被执行」，矩阵解决「检查的规则对不对」。前者是工程问题，后者是需求问题，混在一起就会出现「中间件挂好了，规则还是空的」。

### 节点 4 · 合并与 CI：产出可重复的机械检查

SSDF 里 PW.7 是「审查或分析人类可读的源码以识别漏洞并核对安全要求」，PW.8 是「测试可执行代码以识别漏洞并核对安全要求」。两个实践分开列，是因为它们本来就是两件事：一个看源码，一个跑程序。不少流水线只做了前者，把「扫过」当成「测过」。

负向用例长这样，断言的是「不能」：

```python
def test_cannot_download_attachment_from_others_ticket(client, user_a, ticket_of_b, file_of_b):
    r = client.get(
        f"/api/tickets/{ticket_of_b.id}/attachments/{file_of_b.id}",
        headers={"Authorization": f"Bearer {user_a.token}"},
    )
    assert r.status_code in (403, 404)
```

再加一条纯形态的合并检查：新增路由如果带路径参数或资源 ID，却没有归属条件或写明理由的豁免记录，就挡住合并。这条检查不需要理解业务，只认路由形态和文件里有没有对应的负向用例，因此能进 CI 每天跑。

关键限制也在这里：CI 只能检查已经定义过的规则。矩阵里没写的那一格，流水线会安安静静地放过。左边定义得越含糊，右边越安静——这就是「加了扫描仍然漏」的完整解释。

### 节点 5 · 测试与预发：产出负向用例集与配置复核

OWASP Top 10:2025 的 A01 仍是失效的访问控制，映射了 40 个 CWE，是贡献数据中出现次数最多的一类。它的预防建议里有一句很具体：开发者和 QA 应当把功能级访问控制纳入单元测试与集成测试。不是「上线前让安全团队扫一遍」，是和功能测试同一个仓库、同一次运行。

负向用例至少覆盖这几种形态：改外层 ID、改内层 ID、换租户、去掉凭证、凭证过期、普通角色调管理接口。再补一项配置复核：判定失败时要安全退出，错误响应不带出系统日志或调试信息，失败处理集中在一处（Cheat Sheet 的「授权检查失败时安全退出」，对应 CWE-209）。

### 节点 6 · 发布与上线：产出默认安全配置、审计记录、反馈回路

SSDF 的 PW.9 要求软件默认带安全设置，PS.3 要求归档每个发行版所需的文件及支撑数据（完整性校验信息、来源信息），RV.1 要求持续识别并确认漏洞，RV.3.1 则是一句动作：分析已识别漏洞的根因。

审计表把发起人和资源归属放在同一行，「过去一段时间有没有越界访问」才成为能查的问题：

```sql
CREATE TABLE access_audit (
  id            BIGSERIAL PRIMARY KEY,
  actor_id      BIGINT NOT NULL,
  tenant_id     BIGINT NOT NULL,
  resource_type TEXT   NOT NULL,
  resource_id   BIGINT NOT NULL,
  owner_id      BIGINT NOT NULL,
  action        TEXT   NOT NULL,
  decision      TEXT   NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

右边不是左移的反面，是左移的输入。RV.3.1 落到日常动作就是：每查到一次越界访问，回写一条「矩阵哪一格没写、哪条负向用例没覆盖、哪次变更没触发重审」，然后去改对应的左边产物。缺了这条回路，同一个形态下个版本还会再来一次。判断左移有没有做完，就看这条回路通不通——上线发现的东西，能不能改回需求和 CI 里去。

## 三、把六个节点串起来

| 节点 | 必须交出的产物 | 可核查判据 | 漏了会怎样 |
|---|---|---|---|
| 需求评审 | 角色 × 资源 × 操作的授权矩阵、信任边界 | 每一格指到文件与段落，未写操作默认拒绝 | 业务上「允许什么」没有定义，后面全靠猜 |
| 设计评审 | 自动导出的接口清单、威胁模型、豁免理由 | 由未参与设计者或工具链复核设计 | 只画正常路径，攻击路径无人负责 |
| 编码 | 归属条件与资源 ID 同条件的查询、全局中间件 | 双层资源逐层绑定，检查在可信服务层 | 改内层 ID 就能读到别人的数据 |
| 合并与 CI | 负向用例、新增路由的形态检查 | 用例随功能测试一起跑，路由变更触发重跑 | 规则没定义的部分被安静放过 |
| 测试与预发 | 负向用例集、失败处理与配置复核 | 覆盖换租户、去凭证、越权调管理接口 | 检查写了却在异常路径上被绕过 |
| 发布与上线 | 默认安全配置、审计表、根因回写 | 发起人与资源归属在同一行；根因改回矩阵 | 同类问题下个版本重复出现 |

## 四、最小落地顺序，别一次铺开

一个下午能做完三件事：

1. 从路由表导出带资源 ID 的接口清单，标出写操作和管理类接口。
2. 挑一个最敏感的读接口，补一条负向用例，接进 CI 跟功能测试一起跑。
3. 加一条合并检查：新增带路径参数的路由，必须有归属条件或写明理由的豁免记录。

跑完当天就能拿到第一批真实结论：带资源 ID 的接口里有多少写了归属条件、有多少有负向用例。这两个数能涨能跌、能复核、能指定负责人，比「我们左移了」有用得多。之后再补矩阵与审计表，最后把变更触发重审接上。

## 五、两个常犯的反模式

**工具越加越多，规则没人维护。** 症状是告警堆积、开发者学会忽略红色标记。根因是把左移理解成采购动作，没给每类告警指定一个负责的节点和一份该改的产物。治法很机械：每一条规则都得能指回矩阵里的一格，或指回一条写清楚的标准条款；指不回去的先关掉，别留着刷存在感。

**矩阵写完就锁进文档。** 症状是权限模型从单租户改成多租户，代码一行没改，风险等级变了；没有任何一行 diff 是「写错」的，错的是少了一行，而少了的东西不出现在 diff 里。治法是把矩阵和路由清单绑在一起，路由一变就重跑矩阵，把根因记录变成矩阵的变更记录，而不是事故复盘里的一段话。

两个反模式是同一个根因：决策点没有负责人，也没有回流通道。工具和文档都不会自己更新，只有把「谁改矩阵、改完谁重跑」写进流程，左移才会从一句口号变成持续生效的东西。

## 把清单固定下来

靠人记「谁该看谁的数据」不牢，因为人换了、接口加了、权限模型从单租户改成多租户，没人会回头把那一格结论重念一遍。

能机械判的那几项，交给每次都跑的检查更靠谱。带资源 ID 的查询有没有把归属条件和 ID 写进同一个条件里、写操作有没有取到当前用户身份、新增路由有没有对应的负向用例、管理类接口有没有独立的认证依赖与审计字段。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事：7 大规则引擎把能从代码结构里读出来的形态逐条跑一遍。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
