# 等保 2.0 供应链安全怎么落地：代码审查证据、依赖清单和漏洞修复记录

先给结论：等保 2.0 里跟软件供应链有关的条款，绝大多数问的是「证据在不在」，不是「买了什么设备」。中小团队测评前卡住的地方，通常也不是技术做不到，而是交付包里没有能翻页核对的东西——安全测试报告只有一句「测试通过」，依赖表里两条没写版本，外包方交了源码却没人写过审查说明。

顺带纠一个常见说法：这些条款不是 2.0 才凭空新增的。GB/T 22239-2008（等保 1.0）的「系统建设管理」里已经有「产品采购和使用」「外包软件开发」「安全服务商选择」，外包软件开发那条甚至已经写了「提供软件源代码，并审查软件中可能存在的后门」。2.0 改的是范围和义务链：保护对象从信息系统扩到网络以及云、移动互联、物联网、工控等场景；「服务供应商选择」要求明确**整个服务供应链各方**需履行的网络安全相关义务；云计算安全扩展要求里还单列了「供应链管理」控制点。把 2.0 理解成「新加了一章、要采购新设备」，方向从一开始就偏了。

## 一、把「供应链安全」拆成控制点，别当成一个词

GB/T 22239-2019 没有一章叫「供应链安全」。相关要求散在安全通用要求的「安全建设管理」（三级为 8.1.9）、「安全运维管理」（三级为 8.1.10），以及云计算安全扩展要求的「供应链管理」里。逐条翻译成「交付包里该有什么」：

| 控制点 | 标准要求的原意 | 交付包里该有的证据 |
|---|---|---|
| 产品采购和使用 | 网络安全产品、密码产品采购合规；三级要求预先做选型测试、确定候选范围并定期审定更新候选产品名单 | 选型测试记录、候选产品名单及审定记录 |
| 自行软件开发 | 开发环境与运行环境分开；三级要求制定代码编写安全规范，对程序资源库的修改、更新、发布授权批准并严格版本控制 | 代码安全规范、发布审批与版本记录 |
| 外包软件开发 | 交付前检测可能存在的恶意代码；提供软件设计文档和使用指南；三级还要求提供源代码，并审查软件中可能存在的后门和隐蔽信道 | 检测记录、设计文档、使用指南、源码包、后门与隐蔽信道审查说明 |
| 测试验收 | 制订验收方案并形成报告；上线前做安全性测试并出具安全测试报告，三级要求报告含密码应用安全性测试相关内容 | 验收方案、验收报告、含具体用例的安全测试报告 |
| 系统交付 | 制定交付清单并清点设备、软件和文档；培训运维人员；提供建设过程文档和运行维护文档 | 逐项可勾的交付清单、培训记录、两类文档 |
| 服务供应商选择 | 选择合规；签订协议明确整个服务供应链各方的安全义务；三级要求定期监督、评审和审核服务，并控制服务内容变更 | 合同附件、定期评审记录、变更控制记录 |
| 漏洞和风险管理 / 配置管理 | 识别安全漏洞和隐患并及时修补或评估影响后修补；记录并保存软件组件、组件版本和补丁信息等基本配置 | 漏洞台账、补丁记录、组件版本清单 |
| 云计算扩展·供应链管理 | 供应商选择合规；把供应链安全事件信息或安全威胁信息及时传达到云服务客户 | 事件通报机制与传达记录 |

看清楚一件事：这八行里，要求产出的是**文件、记录、清单、报告**，没有一行要求新增一台硬件。三级比二级多出来的几项（选型测试与候选名单、代码安全规范与版本控制、源代码与后门审查、验收报告里的密码应用内容、定期监督评审）也全都是「多做一次并留痕」。这对中小团队其实是好消息：成本主要在流程和习惯，不在预算。

## 二、一份交付包的实跑清点：10 项里只有 2 项齐备

光讲条款没感觉。我写了一个纯标准库的静态清点脚本，对一个故意留缺口的演示交付包跑了一遍：不联网、不启服务、不装包，只列文件、读文本、匹配关键词。实跑输出如下，数字全部来自这次运行：

```text
=== 交付包证据清点（本地静态，不联网、不启服务） ===
文件 7 个：README.md / app.py / docs/delivery_checklist.md / docs/design.md
           / docs/security_test_report.md / order_service.py / requirements.txt
Python 源码 2 个，共 33 行
依赖声明 4 条：requests>=2.31 / flask / PyYAML==6.0.2
               / git+https://example.com/internal-tools.git@v0.3
  固定版本 1 / 未固定版本 2 / 非 registry 来源 1 / 锁文件或哈希文件 0
  未固定：requests>=2.31 / flask
  非 registry 来源：git+https://example.com/internal-tools.git@v0.3
条款证据对照（10 项，文档 4 份）：
  [缺] 产品采购和使用（选型测试 / 候选名单）
  [缺] 自行软件开发（代码安全规范 / 版本控制）
  [缺] 外包软件开发 a（交付前恶意代码检测）
  [齐] 外包软件开发 b（设计文档 + 使用指南）
  [部] 外包软件开发 c（源码 + 后门与隐蔽信道审查）
  [不] 测试验收 b（上线前安全测试报告，含用例）
  [齐] 系统交付 a（交付清单）
  [缺] 服务供应商选择 b/c（协议 + 定期监督评审）
  [不] 配置管理 / 漏洞和风险管理（组件版本、补丁、漏洞台账）
  [缺] 云扩展 供应链管理 b（安全事件信息传达）
汇总：齐 2 / 部分 1 / 不合格 2 / 缺 5
```

两个「齐」恰好都是「有没有这份文档」，也是测评前最容易临时补出来的两样。剩下八项值得逐个看：

**安全测试报告不合格。** 演示包里那份报告写的是「结论：安全性测试通过，未发现高危问题。测试范围：功能与安全配置」。没有用例、没有断言、没有期望返回码，也没提密码应用安全性测试。这份文件证明不了任何东西被验证过，只证明有人写过一句结论。

**配置管理不合格。** 4 条依赖里 2 条没固定版本、1 条从 git 地址直装、锁文件和哈希文件为 0。测评问「线上跑的到底是哪个组件版本、打了哪些补丁」，靠这张表答不上来。更麻烦的是 `flask` 这种不带版本的写法，今天装到的版本和下个月装到的可能不是同一个。

**「部分」那项最容易吃大亏。** 源码交了，但三级要求的「审查软件中可能存在的后门和隐蔽信道」没有留下任何说明。T/ISEAA 001-2020《网络安全等级保护测评高风险判定指引》里，「外包开发代码审计措施缺失」被列为三级及以上系统的高风险判例，对应的标准要求正是这一句。只交源码、不交审查说明，等于这一条没做；而高风险项在测评里是要单独处置的。

清点脚本只判断「文件在不在、关键词有没有」，不判定合规，也不看代码写得对不对。它在这里的作用是把「我们材料应该齐了」这句感觉，换成能数出来的 2 / 1 / 2 / 5。

## 三、条款真正要的是一条能复核的证据链

按上面的缺口分类，补法不一样，别一视同仁地「补文档」。

**源码与审查说明。** 要求不是让人把几万行代码通读一遍，是留一份能复现的记录：审查范围（哪些入口、哪些依赖）、用了什么检查手段、发现了什么、怎么处置、谁签的字。能机械判的形态可以写死成清单——代码里的外连地址、动态执行与反序列化入口、凭据字面量、隐藏路由与调试端点、安装与启动钩子、构建脚本里的远程下载。命令行就能起个头：

```bash
git grep -nE '(eval|exec|pickle\.loads|subprocess|socket\.connect)[[:space:]]*\(' -- '*.py'
git grep -nE '(SECRET|TOKEN|PASSWORD|API_KEY)[[:space:]]*=' -- '*.py' '*.yaml' '*.yml'
git grep -nE '(curl|wget|git\+https|pip install)[^#]*' -- 'Dockerfile' '*.sh' '*.yml'
```

三条命令给的是形态，不是结论。命中了要人工判，没命中也不代表安全——这份边界得写进审查说明里，否则又变成一句「未发现异常」。

**依赖清单与 SBOM。** NTIA 2021 年 7 月 12 日发布的《软件物料清单（SBOM）最低要素》给了七个基准字段：供应商名称、组件名称、组件版本、其他唯一标识符、依赖关系、SBOM 数据作者、时间戳；要求机器可读（SPDX、CycloneDX、SWID 之一），且每个新版本重新生成。同一份文件里「实践和流程」部分有一项对中小团队特别实用：**明确的未知**——依赖关系有没有穷举、哪里还不知道，要写出来，不许留白。这正好接上「配置管理」要求的组件、版本和补丁信息。PyPA 维护的 `pip-audit` 能审计环境、requirements 文件和本地项目，可输出 CycloneDX 格式；npm 官方 `npm audit` 默认依赖 `package-lock.json` 或 shrinkwrap，绕过锁文件后每次重建依赖树结果会不一样。两个工具都要在流水线里跑，理由不是「这次有漏洞」，而是新的公告会在代码一行没改的前提下让构建变红。

这里也要说清边界：这类工具比对的是已知公告与版本，不看你有没有真的调用那个危险函数，也挡不住还没进公告库的恶意包。「扫描通过」不等于「代码安全」，别把工具的能力范围擅自放大一圈。

**安全测试报告要有用例。** 报告里得能翻到断言的那几行，并且能在本地跑通。例如负向用例应写成 `assert r.status_code in (403, 404)`，而不是「权限校验正常」。三级还要求报告含密码应用安全性测试相关内容，这一句常被整段漏掉。

**供应商协议与定期监督。** 「服务供应商选择」那条 b 要求协议明确**整个服务供应链各方**的义务——外包方引入的第三方组件也归它管，不能只约束乙方自己写的代码；c 要求定期监督、评审、审核并控制服务内容变更，是持续动作，不是签一次合同就完。合同附件里写明组件清单义务、公告告知时限、升级责任，比事后追责有用。

**事件通报。** 云计算扩展的「供应链管理」要求把供应链安全事件信息或威胁信息及时传达到云服务客户。中小团队常把自己只当成「客户」，但只要给甲方交付系统，你就同时在别人的供应链里：上游组件出了公告，你得有能力在几小时内列出受影响版本并通知到对方。这一条平时不显眼，出事时是唯一能证明你尽到义务的记录。

## 四、把证据变成构建的副产物，别测评前补

上面所有缺口，靠测评前一周集中补材料也能补上一次。问题是它是一次性博弈：依赖一升级、外包方一换人、接口一加，缺的证据又回来一遍，而且每次都得重新谈「这算不算额外工作量」。

治本的做法是把证据生成挂进流水线，让它跟构建一起产出。目录结构可以很朴素：

```text
delivery/
  src/
  requirements.txt            # 或 package.json + package-lock.json
  sbom.cdx.json               # 机器可读清单，每个发布版本重新生成
  docs/design.md              # 设计文档
  docs/usage.md               # 使用指南
  docs/delivery_checklist.md  # 逐项可勾的交付清单
  docs/security_test_report.md
  docs/source_review.md       # 源码与后门、隐蔽信道审查说明
  docs/vendor_review.md       # 供应商定期评审记录
  evidence/audit_<date>.json  # 公告核对输出
  evidence/build.sha256       # 提交号 + 产物哈希
```

流水线里加几步，都是确定性的事：

```bash
# 1 依赖公告核对 + 机器可读清单（参数名以本机 pip-audit --help 为准）
python -m pip_audit -r requirements.txt -f cyclonedx -o sbom.cdx.json
python -m pip_audit -r requirements.txt -f json -o evidence/audit.json
npm audit --json > evidence/npm-audit.json

# 2 记录「线上跑的是哪一份」
git rev-parse HEAD > evidence/build.sha256
sha256sum dist/*.whl >> evidence/build.sha256

# 3 证据清点：必需文件在不在、报告里有没有断言、依赖有没有锁版本
#   缺一项就让构建红，而不是等测评时才发现
python ci/check_delivery_evidence.py delivery/
```

第 3 步是整条链的关键。前面那节那个清点脚本只有一百行出头，做的事就是「文件在不在、关键词有没有」，把它接进 CI 之后，缺材料会在写代码当天被点名，而不是半年后在测评现场被点名。计数可以每次自动跑，定性必须有人签字——这两件事分开，清单才不会变成走过场的表单。

还有一层二阶影响：证据齐了不等于没有漏洞。访问控制、越权这类问题，从来不是靠交齐文档能挡住的；文档只保证「谁允许看谁的数据」这个决定被写下来、被复核过。把合规当成安全上限，比不做合规更危险。

## 五、三种常见误判，其实是同一个根因

**把合规当采购。** 以为过测评靠加设备。上面八个控制点里绝大多数是管理要求，产出是记录。设备能解决「有没有」，解决不了「哪一天、谁、验了什么」。

**把报告结论当证据。** 「安全性测试通过」「未发现高危」这类句子无法复核，签字之后没人能推翻它。能复核的是用例、断言、返回码和复现命令。

**把一次性补材料当流程。** 今年补完，明年依赖升级、外包换人，又缺一遍。

三者的根因是同一个：**只确认了「材料交了」，没有建立「下次还会在」的机制**。补材料是按次数付费，做成构建副产物是一次性成本；随着接口数和依赖数增长，前者的账会越滚越大。

## 六、一个下午能做完的最小动作

按这个顺序推，不需要额外采购：

1. 按第一张表逐行问一遍「这份证据在哪个文件」，把答不上来的行记成缺口清单。
2. 把依赖表里没固定版本的补全，锁文件进版本库，生成一份机器可读清单。
3. 把安全测试报告从「结论」改成「用例 + 断言 + 复现命令」，三级系统补上密码应用安全性测试相关内容。
4. 给源码补一份审查说明：范围、手段、发现、处置、签字人；明确写出哪些地方还是未知。
5. 合同附件里补上整个服务供应链各方的清单义务、公告告知时限与升级责任，并约定定期评审记录怎么留。
6. 建一个 `evidence/` 目录，把构建提交号、产物哈希、公告核对输出自动落盘。
7. 把证据清点脚本接进 CI，缺一项就让构建红。

做完这七步，手里就有了一批能涨能跌、能复核、能指定负责人的东西：10 个控制点里有多少齐备、多少不合格、依赖里还有几条没锁版本。比「材料应该齐了」这句感觉有用得多。先初筛，再上线。

## 把清单固定下来

靠测评前一周补几份文档不牢：依赖一升级、外包方一换人、组件一出公告，缺的那份证据就又没了，没人会回头把每个控制点重问一遍。

能机械判的那几项，交给每次都跑的检查更靠谱。交付清单有没有逐项可勾的文件、依赖有没有固定版本并附锁文件、安全测试报告里有没有能复核的断言、源码与后门审查说明在不在、组件版本和补丁信息有没有进配置台账、供应链安全事件有没有通报记录。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事：7 大规则引擎把能从代码结构里读出来的形态逐条跑一遍。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
