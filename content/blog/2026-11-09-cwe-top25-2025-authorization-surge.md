# CWE Top 25 2025 解读：越权和鉴权类漏洞集体上冲，AI 写代码最容易漏的正是这些

2025 年 12 月 11 日，CISA 联合 MITRE 发布了 2025 年度 CWE Top 25 最危险软件弱点榜单。数据集是 NVD 里的 39,080 条 CVE 记录，按「出现频率 × CVSS 严重度」加权打分。榜单年年发，今年真正值得看的是位次变化：**涨得最猛的几类，全是「没被要求写就不会出现」的代码**——恰好是 AI 生成代码最不设防的地方。

## 一、前排格局：XSS 断层第一

第一名 XSS（CWE-79）拿到 60.38 分，第二名 SQL 注入（CWE-89）28.72 分——头名是次名的两倍还多，这在历届榜单里都是罕见的断层。CSRF（CWE-352）升一位排第三。

第四到第十：缺失授权（CWE-862）、越界写入（CWE-787）、路径遍历（CWE-22）、释放后再使用（CWE-416）、越界读取（CWE-125）、操作系统命令注入（CWE-78）、代码注入（CWE-94）。

前十里唯一升幅大于一位的是 CWE-862 缺失授权，比去年直接升了 5 位。这不是噪音，是趋势的起点。

## 二、涨得最猛的四类，缺陷全在「没写的那行」

把整个榜单按位次变化排一遍，上升最多的是：

| 弱点 | 编号 | 位次变化 | 现在排第几 |
|---|---|---|---|
| 空指针解引用 | CWE-476 | +8 | 13 |
| 用户可控键绕过授权（IDOR） | CWE-639 | +6 | 24 |
| 缺失授权 | CWE-862 | +5 | 4 |
| 关键功能缺少认证 | CWE-306 | +4 | 21 |

再把「谁被允许做这件事」这一族算全：CWE-862（第 4）、CWE-863 授权不正确（第 17）、CWE-284 访问控制不当（第 19）、CWE-200 敏感信息暴露给未授权方（第 20）、CWE-306（第 21）、CWE-639（第 24）——**授权和鉴权类弱点占了 25 席里的 6 席**。

这四类上升的有一个共同点：它们的缺陷都不在写出来的代码行里，而在压根没写的那一行里。没有错误的 SQL，没有拼接的命令，没有越界的下标——只有一个本该存在却缺席的检查。

## 三、为什么 AI 写的代码最容易栽在这里

AI 生成代码的强项，是把需求描述清楚的功能忠实地实现出来。而授权检查、认证依赖、空值防护有一个共同特征：**需求里不提，它就不会出现**。AI 不会替你补一句「等等，这个接口是不是该先确认调用者是谁」——它不知道你的权限模型，需求文档里没写的东西对它就不存在。

看两段 AI 一分钟就能生成、而且看起来完全没问题的代码。

第一段，缺失授权（CWE-862），需求是「管理员可以停用账号」：

```python
@router.post("/api/admin/users/{user_id}/disable")
def disable_user(user_id: int, db: Session = Depends(get_db)):
    user = db.get(User, user_id)
    if user is None:
        raise HTTPException(status_code=404, detail="用户不存在")
    user.is_active = False
    db.commit()
    return {"ok": True}
```

代码把需求实现得很完整：查用户、判空、停用、提交。没写的是——**调用者是不是管理员**。函数签名里连当前用户的影子都没有。功能测试照样全绿，因为测试用例也是照着需求写的，测试的人就是「管理员」。

第二段，空指针解引用（CWE-476）：

```python
def get_user_city(user_id: int, db: Session):
    profile = db.query(Profile).filter(Profile.user_id == user_id).first()
    return profile.city
```

`first()` 在没有匹配行时返回 `None`，下一行直接解引用。AI 假设数据总是齐的——因为需求里没有人告诉过它「这个用户可能还没填资料」。

IDOR（CWE-639）是同一族的第三种形态：查询条件里只有资源 ID，没有归属条件。把请求里的订单号换成别人的，接口照样返回数据。

这三段代码还有一个更麻烦的共性：**它们在 diff 里是看不见的**。代码评审看的是改动，自动测试跑的是断言，两者都以「写了的代码」为对象。一段根本不存在的授权检查，不会出现在任何一行的改动里，也就不会被任何盯着改动看的流程发现。

## 四、降的类别同样在说话：剪刀差才是信号

榜单另一头，下降最狠的是：命令注入（CWE-77）跌 10 位到第 23，输入验证不当（CWE-20）跌 6 位到第 18，SSRF（CWE-918）跌 3 位到第 22。

注入类的特点是「写了的行写错了」：特征明确、参数化查询和 ORM 框架默认防护、被安全教育盯了三十年、检测工具查得准。所以这类漏洞在稳定下降。

「缺席类」正相反：没有可匹配的特征字符串，框架不替你管，需求文档里不写就没有。想查它，工具必须换思路——不是找「哪一行写错了」，而是找「这个接口本该有身份依赖却没有」「这次查询本该带归属条件却没有」。

一升一降组成的剪刀差，就是榜单给出的信号：**行业把「写错的代码」管得越来越好，「没写的代码」正在成为漏洞的主要来源**。而 AI 编程工具的大量使用，恰好在加速这个剪刀差——它把「写出来」的成本降到了接近零，但「想起来要写」这件事，始终没有降成本。

有一处要说明白，免得误读：命令注入排名跌了 10 位，不等于可以不防。在 CISA 的 KEV 目录（已知被野外利用的漏洞清单）里，CWE-78 名下挂着 20 条记录，是全榜单最多的几类之一。排名降说的是新披露量在降，攻击者手里囤的老武器一点没少。榜单用来排优先级，不用来删待办。

照着榜单查自己的代码，四条就够：

1. 每个接口问一句：调用者身份从哪来，落在代码哪一行？（对应 CWE-862 / CWE-306）
2. 凡是拿 ID 查资源的，归属条件和 ID 必须出现在同一个查询条件里。（对应 CWE-639）
3. 管理类接口单独确认认证依赖，不假设「网关已经挡住了」。（对应 CWE-306）
4. 所有 `first()` / `get()` 的返回值，用之前判空。（对应 CWE-476）

第 1、2 条要能**指出具体行号**。答「应该有吧」「框架会处理」等于没有。

## 五、溯源与参考

- 榜单排名、分数、位次变化取自 CISA 与 MITRE 于 2025-12-11 发布的 2025 CWE Top 25（cwe.mitre.org/top25/），数据集为 NVD 中 39,080 条 CVE 记录，评分方法为普遍性与 CVSS 严重度加权。
- CWE-862、CWE-639、CWE-306 等条目的定义见 cwe.mitre.org 对应页面；IDOR 的分类口径参考 OWASP API Security Top 10 的 API1（对象级授权失效）。
- 文中两段代码是可运行的最小示例，取自 FastAPI + SQLAlchemy 的常见写法；差异集中在身份依赖与判空两处，没有其他改动。
- 「AI 生成代码容易漏掉需求未写明的约束」的论证，依据是本系列前两篇已发布文章的同一口径：Code Review 与功能测试都以「写了的代码」为对象，缺席的约束不在其视野内。

## 六、把清单固定下来

榜单半年更一次，代码天天在写。这四条靠人逐个接口念，能挡住大半；但「缺席」这种缺陷，代码照样全绿、功能照样正常，不点名它就永远不出现。

能机械判的那几项，交给每次都跑的检查更靠谱。接口有没有身份依赖、资源 ID 的归属条件有没有跟 ID 同行出现、管理类接口有没有单独的认证依赖、first() 和 get() 的返回值有没有判空。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
