# 代码审查为什么总漏掉越权漏洞：评审看的代码，和攻击走的路径不是同一条

先说结论：代码审查查不出大部分安全问题，不是评审的人不认真，是两边看的东西根本不重合。

评审看「这段代码写得对不对」，攻击问「这件事本来该不该被允许做」。前者的证据在改动里，后者的证据常常是一行根本没写出来的代码。没写出来的东西不会出现在改动里，评审再认真也看不见。

## 一、一段能顺利通过评审的代码

下面这段是 FastAPI + SQLAlchemy 里很常见的写法：

```python
# app/api/order.py
@router.get("/api/orders/{order_id}")
def get_order(order_id: int, db: Session = Depends(get_db)):
    order = db.query(Order).filter(Order.id == order_id).first()
    if order is None:
        raise HTTPException(status_code=404, detail="订单不存在")
    return OrderSchema.from_orm(order)
```

评审看到这段会问：类型标注有没有、404 处理了没有、查询会不会 N+1、返回结构对不对。这几项都过。

功能测试也过：下单 → 拿到 order_id → 请求 → 返回自己的订单。全绿。

问题在于 `order_id` 来自路径，函数里没有任何一处把「当前登录的人」和「这条订单属于谁」对上。把地址栏里的数字换成别人的，接口照样返回数据。

修法只有两行：

```python
@router.get("/api/orders/{order_id}")
def get_order(
    order_id: int,
    current_user: User = Depends(get_current_user),      # 新增
    db: Session = Depends(get_db),
):
    order = (
        db.query(Order)
        .filter(Order.id == order_id, Order.user_id == current_user.id)  # 新增
        .first()
    )
    if order is None:
        raise HTTPException(status_code=404, detail="订单不存在")
    return OrderSchema.from_orm(order)
```

留意这次改动的形状：加的是两个「本来就该有、但从来没被要求写」的条件。第一版代码没有任何一行是错的，所以评审挑不出错。少的是约束，不是语句。

这就是第一层原因。

## 二、三处结构性的错位

**错位一：改动里没有「缺席」**

评审的原材料是 diff。命名、格式、边界、异常、可读性，都能在改动里被指出来。权限约束这类东西，写错会被看见，不写不会被看见——因为没有任何一行标着「这里缺了鉴权」。

一个接口上线前该有的约束，通常还散在别处：全局中间件、路由注册时的依赖、网关策略、框架默认配置。它们可能在别的 PR、别的仓库、甚至别的服务里。看单个 PR 的人手上没有那个上下文。

**错位二：评审跑正常路径，攻击走异常路径**

评审在脑子里模拟的是「用户按产品设计的用法点一遍」。攻击者不按设计走：换 ID、改请求体里的 user_id、把 POST 换成 GET、删掉某个 header、把两步操作并成一步并发发。

这几类动作在功能测试里通常没有用例，理由往往是「正常用户不会这么干」。可接口并不知道对面是不是正常用户。

**错位三：评审判断「像不像好代码」，安全判断「允不允许」**

两者的评价标准不一样。一段代码可以写得非常干净：参数校验齐全、错误码规范、有单测、有注释，同时完全没有权限模型。评审给通过是合理的——按代码质量的标准它确实写得好。

问题出在团队把「代码审查通过」当成了「安全检查通过」。这是两件事。

## 三、把「缺席」变成能被问出来的问题

缺席的东西看不见，但可以被点名。下面这份清单不依赖任何工具，评审时逐条念一遍，就能覆盖接口层最常见的问题。

| # | 要问的话 | 在找什么 |
|---|---|---|
| 1 | 这个接口靠什么确认「是谁在调」？在代码哪一行？ | 身份来源，不能只答「有网关」 |
| 2 | 传入的资源 ID，和当前身份在哪一行对上？ | 对象级越权（IDOR） |
| 3 | 写操作有没有单独校验权限，还是复用了读接口的逻辑？ | 读写权限混淆 |
| 4 | 请求体里的用户 ID、角色、价格，服务端信不信？ | 客户端可控字段 |
| 5 | 错误分支会不会把内部信息带出去？ | 信息泄露 |
| 6 | 这个动作重放一次、并发两次，会发生什么？ | 幂等与竞态 |

第 1、2 条要能**指出具体行号**。答「应该有吧」「框架会处理」等于没有。

再补一条流程上的做法：把权限模型写进接口设计，而不是写完代码再补。设计文档里先列清楚每个接口谁能调、能操作谁的数据，评审时对着这张表看，缺席项就有对照物了。

## 四、自动检查能补哪一段，补不了哪一段

自动检查适合干「点名」这件事：接口有没有引入身份依赖、资源 ID 有没有和身份关联、客户端可控字段有没有被服务端覆盖。这些是形态，能从代码结构里读出来，跑得快、不疲劳、不会因为是周五下午就漏看。

补不了的是业务语义。「客服能不能代查订单」「外包方能不能看到未发布的素材」——这类答案在产品规则里，不在代码里。把它们写进设计文档、变成上面那样的清单，才是人该干的部分。

两者叠起来才有意义：机器负责每次都不漏地扫形态，人负责定义什么叫「允许」。

## 五、溯源与参考

- 文中两段接口代码是可运行的最小示例，取自 FastAPI + SQLAlchemy 的常见写法；差异集中在身份依赖与查询条件两处，没有其他改动。
- 「对象级越权」的分类口径参考 OWASP API Security Top 10 的 API1（对象级授权失效），以及 OWASP Top 10 的 A01（访问控制失效）。
- 六条评审清单按「身份 → 归属 → 写权限 → 可控字段 → 错误分支 → 重放」排列，对应接口从入口到落库的检查顺序，不是按严重程度排序。

## 六、把清单固定下来

上面六条靠人逐条念，能挡住大部分问题。但人会漏、会赶时间、会在周五下午想早点下班，而「缺席」这种东西不盯着就永远看不出来。

能机械判的那几项，交给每次都跑的检查更靠谱。接口有没有引入身份依赖、资源 ID 有没有和当前身份对上、客户端可控字段有没有被服务端覆盖。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
