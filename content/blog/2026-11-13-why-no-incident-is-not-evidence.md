# 「代码上线三年没出过事」为什么不可信：代码审查该查的不是事故记录，是接口里越权漏洞的证据链

一次上线评审，负责人说：这套系统跑了三年，没出过事，代码质量应该没问题。

说这话的人很真诚。监控确实没报过安全类告警，工单里没有相关事故，客户也没投诉过数据串号。问题不在这句话是假的，在于它被放错了位置：它描述的是一个**观测结果**，却被当成了一个**安全结论**。中间少了整整一层举证，而这一层恰恰是上线决策真正需要的东西。

把这句话拆开，再换成能核查的东西，比争论「到底安不安全」有用得多。

## 一、「没出事」是三句不同的话，被压成了一句

它至少混了三个判断：

1. 三年里没有**观测到**异常。这取决于有没有看、看的是哪几个指标、日志留了多久。
2. 三年里没有**发生**被利用的攻击。这取决于攻击者来没来、来了有没有留下痕迹、有没有人把痕迹认出来。
3. 系统当前**不存在**可被利用的缺陷。这是唯一跟「能不能上线」直接相关的一句。

前两句说的是历史，第三句说的是当下状态。用历史去证明当下，要跨过两个缺口：观测能力是否覆盖得过，以及这三年里代码和部署变了多少。两个缺口只要有一个没补上，推论就不成立。

还有个更实际的问题：举证责任落在谁身上。「没出事」本质上是「我手头没有反例」，而没有反例在逻辑上证明不了「所有入口都写了校验」。这不是抬杠。落到工程上，差别非常具体——你要论证的不是「过去没被人发现过」，而是「每个带资源 ID 的数据入口都写了归属条件」。前者无法验证，后者可以逐行数出来、逐条跑测试。

所以评审会上正确的追问不是「真的没出过事吗」，而是「接口清单在哪、鉴权矩阵在哪、负向用例跑过没有」。前一句问完还是零信息，后三句问完能拿到文件、行号和测试结果。

## 二、越权漏洞天生不会变成一条「事故」

看两段同一个接口的写法：

```python
# 缺归属条件：请求者是谁、这张订单归谁，代码里都没有问
@app.get("/api/orders/{order_id}")
def get_order(order_id: int, db: Session = Depends(get_db)):
    return db.query(Order).filter(Order.id == order_id).first()
```

```python
# 归属条件和资源 ID 落在同一个查询条件里
@app.get("/api/orders/{order_id}")
def get_order(order_id: int, user: User = Depends(current_user),
              db: Session = Depends(get_db)):
    return (db.query(Order)
              .filter(Order.id == order_id, Order.owner_id == user.id)
              .first())
```

第一段每一行都是对的：参数是整数、查询是参数化的、ORM 用法合规、没有拼接、没有异常。把请求里的 `10086` 改成 `10087`，服务端照样返回一份完整订单，只是那份订单属于别人。

这类请求有四个「不会」：

- 不会报错。业务上它就是一次成功的查询，状态码 200，响应体结构完整。
- 不会触发异常监控。错误率、延迟、超时、堆栈都落在正常区间里。
- 不会让数据变少。数据被复制走，原记录还在，数据主人毫无感觉。
- 不会留下失败痕迹。访问日志里躺着的是一条普通成功请求。

于是「事故数为零」和「越权漏洞为零」之间没有对应关系。前者统计的是**故障**，后者衡量的是**授权约束是否齐备**，这是两张完全不同的表。拿一张去证明另一张，是这类评审里最常犯的错误。

OWASP API Security Top 10 2023 把对象级授权失效列在 API1，原文要求：凡是接收客户端传来的对象 ID、并据此访问数据源的函数，都应实现对象级授权检查。它的预防建议里明写着「编写测试来检验授权机制，测试不通过的改动不许部署」。同一页把这类问题的可检测性标为 Easy——但那个判断的前提是**有人主动去测**。没有负向用例的时候，可检测性就是零，不是「低」。

再往下看观测层。多数团队留的访问日志长这样：

```text
10:22:31 GET /api/orders/10087 200 37ms user_id=1042
10:22:33 GET /api/orders/10088 200 35ms user_id=1042
```

问一句：这是正常浏览，还是在批量拖别人的订单？这两行答不出来。因为日志里既没有资源归属，也没有授权判定的结果，发起人和数据主人这两个信息不在同一条记录里。把审计表补成下面这样，事情才变成可查询的事实：

```sql
CREATE TABLE access_audit (
  id                 BIGSERIAL PRIMARY KEY,
  actor_id           BIGINT NOT NULL,
  action             TEXT NOT NULL,
  resource_type      TEXT NOT NULL,
  resource_id        TEXT NOT NULL,
  resource_owner_id  BIGINT NOT NULL,
  decision           TEXT NOT NULL,
  occurred_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

关键不是字段多，是 `resource_owner_id` 与 `decision` 让「谁在什么时候读了谁的数据」可以被一条查询回放出来。有了它，才谈得上回头查过去一段时间里有没有发起人访问过归属不属于自己的资源。

OWASP API Security Top 10 2019 的 API10（日志与监控不足）讲得很直白：没有日志和监控，几乎无法追踪可疑活动并及时响应；对应的参考条目包括 CWE-778（日志不足）与 CWE-223（遗漏安全相关信息），并指向 ASVS 的 V7（错误处理与日志）和 V4（访问控制）两组验证要求。

补一个边界，免得走向另一个极端：日志解决的是「能不能发现」，不是「能不能发生」。它只能事后回放，拦不住当次请求。所以「我们留了全量日志」也不能拿来当新的「没出事」，它只是证据链里的一环。

## 三、三年这个跨度，本身就在削弱结论

就算三年前确实做过一轮完整审查，那轮结论的覆盖范围也只有当时的代码、当时的部署、当时的权限模型。三年里几乎一定会发生这些事：

| 变化 | 为什么旧结论不再覆盖 |
|---|---|
| 新增接口、导出功能、批量下载 | 新代码根本没经过当初那轮审查 |
| 单租户改成多租户 | 原本「只有自己人用」的假设不成立了 |
| 鉴权中间件重构、网关迁移 | 校验位置变了，部分路由可能绕过 |
| 依赖与框架升级 | 默认值、路由匹配、序列化行为可能变 |
| 外包交付、人员交接 | 约定留在人脑子里，没进代码和文档 |
| 旧版本接口没下线 | 暴露面比文档里写的大 |

多租户改造最典型。系统原本只服务一家公司内部，查订单不带归属条件在当年算不上错；接入第二家客户后，同一行代码变成跨客户的数据泄露。代码一行没改，风险等级变了。更麻烦的是，这类变化不会自动触发复查，因为没有任何一行 diff 是「写错」的——错的是**少了**一行，而少了的东西不出现在 diff 里。

接口与版本没盘点清楚这件事，OWASP API9:2023（资产管理不当）专门列了一条：API 往往比传统 Web 应用暴露更多端点，主机清单和已部署版本清单不更新，旧版本接口、调试端点就会一直留在生产环境。也就是说，「我们审过」和「线上跑的东西全在清单里」是两个独立命题。

结论该有有效期。把三年前的一句话留到今天用，等于拿旧地图找新路。

## 四、把「没出事」换成六项可核查的证据

下面每一项都能落到文件、行号或一条会变红的测试上。

**1. 接口清单。** 从路由表里自动导出所有接口，标出哪些带资源 ID、哪些是写操作、哪些是管理类接口。清单必须生成出来，不能靠人回忆——回忆出来的清单，正是资产管理不当的起点。

**2. 鉴权矩阵。** 角色 × 资源 × 操作，一格一个结论，每个结论指到具体文件与行号。OWASP 的 Broken Access Control 社区页明确建议用访问控制的 matrix 把策略写下来，并指出策略没被文档化时，「什么叫安全」本身就没有定义，谈不上验证。

**3. 负向用例。** 功能测试测的是「能拿到自己的」，负向用例测的是「拿不到别人的」。两者缺一不可：

```python
def test_order_detail_cannot_read_others_order(client, user_a, order_of_b):
    r = client.get(
        f"/api/orders/{order_of_b.id}",
        headers={"Authorization": f"Bearer {user_a.token}"},
    )
    assert r.status_code in (403, 404)
```

断言的是「不能」，不是「能」。这类用例要进 CI，跟功能测试一起跑，不能只在上线前手工点一次。同一套用例还该覆盖换租户、去掉凭证、凭证过期、普通角色调管理接口这几种形态。

**4. 审计字段与留存。** 按上一节的表，每个涉及他人数据的读写记一条，包含归属和判定；只追加、不改写；留存周期按自身合规要求定。有了这张表，「过去一段时间有没有越界访问」才是可回答的问题，而不是靠印象。

**5. 变更触发重审。** 在 CI 里加一条机械检查：新增路由如果带路径参数或资源 ID，却没有归属条件或显式豁免记录，就挡住合并。权限模型、中间件、网关配置一改，把整张鉴权矩阵重跑一遍。这一步把「三年前出过一次结论」改成「每次变更都重新出结论」，是整条链里最治本的一环。

**6. 用覆盖率替代事故数。** 对外汇报改成三个数：带资源 ID 的接口里，有多少写了归属条件、有多少有负向用例、有多少有审计记录。分母是接口总数，分子是已覆盖数。这三个数能涨能跌、能复核、能追责，也能在下次变更时重新算；「事故零起」什么都做不了，它既不随改动更新，也不随覆盖变化。

落地顺序别铺开。先做第 1 项和第 3 项：把带资源 ID 的读接口列出来，逐个补一条负向用例。一个下午能做完，跑完当天就能拿到第一批真实结论——这个结论可能是「十二个接口里九个没写归属条件」，也可能是「全都写了」，两种都比「没出过事」有用。之后补第 2、4 项，最后把第 5 项接进 CI。

回到评审会上那句话。「没出事」可以留着当背景，不能拿出来当结论。该问的是四个问题：接口清单在哪、鉴权矩阵在哪、负向用例跑过没有、审计字段齐不齐。四个都拿得到指到行号的答案，举证才算完成；答不上来，那只是还没被发现的三年。

## 五、溯源与参考

- OWASP API Security Top 10 2023 的 API1（Broken Object Level Authorization）条目：对象级授权检查应覆盖每个接收客户端对象 ID 并访问数据源的函数、预防建议中的授权机制测试与「测试不通过不部署」、以及 CWE-639 引用，见 owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/；API9（Improper Inventory Management）的端点与版本清单要求见同版 0x11-t10 列表页。
- OWASP API Security Top 10 2019 的 API10（Insufficient Logging & Monitoring）：缺少日志与监控时难以追踪可疑活动，列出 CWE-778、CWE-223 与 ASVS V7、V4 的对应关系，见 owasp.org/API-Security/editions/2019/en/0xaa-insufficient-logging-monitoring/。
- 访问控制策略应写成矩阵、策略未文档化即无「安全」定义，见 OWASP 社区页 Broken Access Control（owasp.org/www-community/Broken_Access_Control）；CWE-862 缺失授权、CWE-639 用户可控键绕过授权的定义见 cwe.mitre.org 对应条目。
- 文中 Python 与 SQL 片段是可运行的最小示例，取自 FastAPI、SQLAlchemy 与 PostgreSQL 的常见写法；访问日志行为演示值，用于说明「成功请求里看不出归属关系」，不是任何系统的实测记录。
- 标准与榜单存在版本差异，引用以 2026-11-13 可查到的官方页面为准；落到自己系统的结论前，按实际使用的框架版本与部署方式复核一遍。

## 六、把清单固定下来

没出事是观测结果，不是安全结论。接口加了又改、人换了又走、权限模型从单租户改成多租户，没人会记得回头念一句「这个资源该不该给这个人」。

能机械判的那几项，交给每次都跑的检查更靠谱。带资源 ID 的查询有没有把归属条件和 ID 写进同一个条件里、写操作有没有取到当前用户身份、管理类接口有没有独立认证依赖、新增路由有没有对应的负向用例和审计字段。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
