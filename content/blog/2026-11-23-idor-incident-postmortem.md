# 一次越权漏洞复盘：改一位编号就能读到别人的文档（IDOR），8.85 亿份记录暴露五年，代码审查漏在哪

2019 年 5 月 24 日，一位房产从业者发现自己手里那条文档链接有点不对劲：链接里有一个九位数字，把这个数字加一或减一，浏览器里就换成了另一个人的文件。不是黑客工具，不是零日利用，不需要账号，甚至不需要懂代码。他反复试了几次，确认能拿到同一时间段前后其他交易的文档，于是先联系了那家公司，没得到实质回应，才转给安全记者。

记者复核后确认：这家美国大型产权保险公司的文档站点，大约 8.85 亿份与房产交易相关的记录，最早的日期能追到 2003 年，全部**无需认证**就能读取。里面有银行账号与对账单、抵押与税务记录、社安号、电汇收据、驾照影像。当天下午两点前，公司关掉了提供文档的那个应用。

这起事件常被写成「一个存在了十六年的漏洞」。这句话是错的，而且错得很典型。本文把公开报道与两份监管文件里的日期、数字逐条对齐，先还原时间线，再看代码上到底缺了什么，最后落在最值得复盘的地方：**检测环节其实是成功的，失败的是从发现到关闭的那一整条链。**

## 一、先把时间线摆准：两个「八亿」不是一回事，两个「年份」也不是

复盘最容易出错的地方，是把不同来源、不同口径的数字揉成一句顺口的话。先把话说清楚：

- **8.85 亿**是记者根据站点可枚举的编号范围估算的「文档总量」；SEC 行政令里写的「超过 8 亿份图像」是监管口径下的暴露规模。两者描述的对象不同，不要当同一个数互相印证。
- **2003** 是站点上能取到的最早一份文档的交易年份，说明数据积累了十六年；**不是**缺陷存在了十六年。
- 缺陷本身是 **2014 年 5 月一次应用软件更新**引入的（纽约州金融服务部在指控材料中认定）。从引入到 2019 年 5 月被修复，大约五年。

时间线如下，每一个日期都有公开出处，见文末溯源段：

| 时间 | 发生了什么 | 出处 |
|---|---|---|
| 2003 | 站点上能取到的最早文档所属的交易年份 | 记者 2019-05-24 报道 |
| 2014-05 | 一次应用软件更新引入该设计缺陷 | NYDFS 指控材料转述 |
| 2017-03 | 互联网档案馆快照显示文档至少从这个时间起已公开可取 | 同上报道 |
| 2018-12 | 公司自己的渗透测试发现了这个缺陷 | NYDFS 指控书、SEC 行政令相关材料 |
| 2019-01 | 内部报告把它定为严重、要求 45 天内整改；却被误录成低风险，落到 90 天整改期 | SEC 行政令及公开法律评述 |
| 2019-05-24 上午 | 记者通知公司；当天 14:00 ET 前关停文档应用 | 记者报道、SEC 新闻稿 |

还有两个数字值得单独记下来，都是关于「到底有没有被人拿走」的：NYDFS 的指控材料提到，公司留存日志覆盖的 11 个月里，超过 350,000 份文档被自动抓取程序访问过；而公司在 2019 年 8 月对外说，第三方调查只确认了 32 名消费者的非公开信息可能被未经授权访问。这两个数并不矛盾——一个说的是「被请求过」，一个说的是「能证明被人看过」，但把它们混着用就会得出完全相反的结论。账面数据必须和「发生过什么」一起读，这里是最直白的例子。

## 二、代码上到底缺了什么：一行归属判断，以及一条没接上鉴权的旁路

先把三件事拆开，代码里它们从来不是同一句 `if`：

- **认证**：你是谁。令牌是否有效、会话是否过期。
- **功能级授权**：你能不能调这个功能。普通用户能不能走导出、批量、管理接口。
- **对象级授权**：这条数据能不能给你。文档存在、你也有读文档的权限，但它是别人的。

OWASP API Security Top 10（2023）把 API1:2023 Broken Object Level Authorization 排在第一位，官方描述里那句话可以直接当判据：**凡是拿用户提供的标识去访问数据源的功能，都要考虑对象级授权检查**。MITRE 的 CWE-639（Authorization Bypass Through User-Controlled Key，别名含 IDOR / BOLA）说的就是「靠改标识绕过」，CWE-862 是压根没做授权检查。这起事件把三者叠满了：没有认证、编号可枚举、按编号直接取对象。

最小形态用几行就能复现，纯标准库，不需要任何框架：

```python
# 错误形态：编号直接查库，没有会话身份，没有归属条件
def get_document_bad(doc_id):
    return db.fetch("SELECT * FROM documents WHERE id = ?", doc_id)
```

```python
# 正确形态：身份只从服务端会话取，归属条件和编号进同一个查询
def get_document_good(doc_id, session):
    if session.user is None:
        raise Unauthorized()
    row = db.fetch(
        "SELECT * FROM documents WHERE id = ? AND owner_id = ?",
        doc_id, session.user.id,
    )
    if row is None:
        raise NotFound()   # 不区分「不存在」和「不是你的」，避免泄露存在性
    return row
```

这里有个特别容易写偏的结论：**顺序编号不是根因**。很多人复盘到这里就写「换成不可猜测的 UUID 就好了」。UUID 只是把「挨个加一」变成「得先拿到链接」，抬高的是枚举成本，没有补上归属判断。链接会通过邮件转发、落进浏览器历史、代理日志、搜索引擎缓存、第三方统计脚本，任何一个环节漏出去，缺归属判断的接口照样把数据交出去。CWE-639 给的缓解方向是「用于查找记录的键不能被外部控制，或者服务端能发现它被改过」，落点始终在服务端校验，不在标识符长什么样。

另一个更该盯的结构：**文档服务是一个独立应用**（NYDFS 文件里叫 EaglePro），不是主站的一个路由。主站有登录态，文档服务没跟上同一套鉴权，于是「整体是登录系统」和「这个入口不需要登录」同时成立。评审看主站的拦截器、看统一的认证中间件，很容易得出「已经做了」的结论；真正漏掉的是那条没被列进接口清单的旁路。OWASP API9:2023 讲存量管理，高发点就在这里：暴露的端点总比想象中多，文件、预览、导出、缩略图、调试路由、废弃版本，都是同一类。

值得说清楚的是，这起事件里的暴露方式是「无需认证即可读」，属于最极端的一端；日常业务里更常见的是温和版本——登录做了，功能级授权做了，唯独对象级授权没写。功能测试、联调、演示走的全是「本人查本人」，谁来都绿，缺的那行判断不会让任何一条用例变红。

## 三、检测成功了，为什么还是拖了半年

这是整份复盘最值钱的一段。很多团队把安全当成「能不能发现」的问题，这起事件给出的答案很不舒服：**发现得很早，一次都没漏，然后照样出事。**

公司内部渗透测试在 2018 年 12 月就找到了这个缺陷，比记者通知早了大约五个月。检测这一环是有效的。往下每一环都断了：

**断点一，定级。** 2019 年 1 月的内部报告把它定为严重、要求 45 天内整改；一名员工把等级误录成「低风险」，系统按低风险给出 90 天整改期。一个下拉框的值，把时钟拨慢了一倍，而且没有任何人复核。等级不是元数据，它直接决定资源、时限和上报路径。

**断点二，影响面。** 团队只复核了 10 份文档，就据此把影响判断成有限，进一步调查的建议没有被采纳。面对上亿份可枚举的记录，抽 10 份推不出面上的结论——抽样范围必须写在结论旁边，否则「本次没发现问题」会被读成「代码很干净」。

**断点三，上报。** SEC 的行政令认定，负责对外披露的高管在签署声明和提交 8-K 时，完全不知道自家安全团队几个月前已经发现该缺陷、且未按公司政策修复。修不修是一回事，该知道的人不知道是另一回事。SEC 那句原话很直白：对投资者重要的信息，必须能传到负责披露的人那里。

**断点四，复验。** 从发现到最终关停，中间没有「有人回头验证过这条缺陷真的被关掉」的证据。整改单上写「已完成」和线上真的不再返回别人的文档，是两件不同的事。

所以两份监管文件罚的都不是那行代码。SEC 依据的是 Exchange Act Rule 13a-15(a)——**披露控制与程序**缺失，罚款 487,616 美元；NYDFS 依 23 NYCRR Part 500 认定的是治理与数据分类、**访问控制与身份管理**、风险评估政策未有效建立（§ 500.3、§ 500.7），2020 年 7 月提出首例该条例下的执法，2023 年 11 月以 1,000,000 美元和解。监管问的是「这套环境是否受控」，不是「有没有一个聪明的攻击者」。

一句话收束：**漏洞在没写的那行代码里，事故在没闭环的那条流程里。** 前者补一行就能修，后者要补的是四个环节各留一条可核对的证据。

## 四、把复盘变成能机械核对的清单

「以后要重视安全」不是结论。能交给检查、每次都跑的是下面这些从代码结构和工单字段里读得出来的形态：

1. **按资源编号读取的入口，归属条件与编号是否在同一个查询里。** 先按编号查出来再到内存里 `if` 判归属，也能挡一部分，但批量接口、缓存层、后加的字段很容易绕开。写进同一个查询最稳。
2. **当前身份从哪里来。** 出现 `owner_id = query.owner_id`、请求体里的 `tenant_id`、`request.user_id` 当归属条件，一律不合格。只认服务端会话或框架注入的当前用户。
3. **旁路路由有没有进接口清单。** 文件、图片、预览、导出、缩略图、独立部署的文档服务，是否和主接口共用同一套鉴权依赖。清单不同步，主站写得再严也有漏网的。
4. **负向用例在不在。** 不是「返回 200 且字段齐全」，而是未登录、换一个账号、换一个租户、编号 ±1 重放，期望 403 或 404。缺一条都不算过。
5. **响应有没有泄露存在性。** 统一返回 404，别让「不存在」和「无权访问」给出不同的状态码或报错文案，那本身就是一份可枚举的目录。
6. **响应字段有没有做属性级过滤。** 直接 `dict(row)` 最容易把归属标识、内部备注、手机号一起带出去。OWASP API3:2023 管的是同一条数据上的第二次判断。
7. **缺陷单的等级和整改期限有没有复核留痕。** 等级被改低、期限被拉长，要有第二个人签字和原因；这类字段直接决定后面四个环节。
8. **每条发现有没有「已修复」加「复验证据」两个字段。** 只有前者，等于把「写完了」当成「关掉了」。复验要能指向一次真实的重放请求。
9. **影响面评估有没有写抽样范围。** 抽了几条、覆盖哪些入口、日志回溯到哪天，写清楚才允许下结论；写不出范围的结论不许进对外声明。
10. **已知未修复的高危项有没有进披露判断链。** 技术团队掌握的信息，要有一条能抵达负责对外表述的人的路径，这是流程，不是自觉。

这份清单的价值在于它不要求评审者当天状态好。每一行都能对着代码、测试文件或工单字段打勾，也能写进提交前的自动检查。业务上「谁允许看谁的数据」得团队自己定义，机器替不了；但「归属条件有没有和编号写在一起」「这条发现有没有复验证据」这种形态，机器能天天盯。

## 五、收尾

回到那个九位数字。它不复杂，任何一个写过按 ID 查询接口的人都看得懂；渗透测试也确实把它找出来了。真正让这份数据在外面挂了五年的，是等级被误填之后没人复核、抽样 10 份之后没人追问、高管不知情、修完没人重放一次请求。

别把预算全押在「能不能发现」上。把上面十条写进每次都会跑的检查，比多买一个能发现同类问题的工具更管用——**检测不是瓶颈，闭环才是**。

## 把清单固定下来

一次渗透测试发现得了越权漏洞，却挡不住它被误填成低风险、拖过整改期、再没人上报——靠人盯流程，总有一环会松。

能机械判的那几项，交给每次都跑的检查更靠谱。带资源编号的读取有没有把归属条件和编号写进同一个查询、身份是不是从服务端会话取、直链和文件路由有没有和主接口共用同一套鉴权、换身份重放的负向用例在不在、缺陷等级被改低有没有留痕、每条发现有没有「已修复 + 复验证据」两个字段。
这些都是形态，从代码结构里读得出来，写代码当天就能被点名，不用等出事。

煋鉴做的就是这件事：7 大规则引擎把能从代码结构里读出来的形态逐条跑一遍。代码贴进 /try 页面，不用登录，扫完直接出报告，按行号写清楚哪一行缺了什么。
业务上「谁允许看谁的数据」还得团队自己定义，机器替不了这个判断。
